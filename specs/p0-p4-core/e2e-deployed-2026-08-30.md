## 缺陷

### F1 [中] 筛选落空时告诉有档案的用户"还没有已上传的文档" — 已修复 `50486f1`

空态只判断筛选后结果集是否为空，未区分"确实没有文档"与"筛选后无匹配"。任何筛选器落空，
都会对着实际存有病历的用户显示"还没有已上传的文档"并邀请其"导入第一份医疗记录"。
在以"记录一直在"为核心承诺的医疗归档应用里，这会让人以为数据丢了。

- 复现：成员「向沐然」实有 1 份文档 `d5ke69` → 文档类型筛选「处方」
- 范围：搜索、日期区间、文档类型、就诊筛选 均触发
- 位置：`apps/web/src/features/browse/BrowseView.tsx`
- 修复：独立空态，说明原件仍在档案库，并提供「清除筛选」

### F2 [中] TSV 粘贴框的示例本身会被解析错位 — 未修

占位符演示 5 列 `项目/结果/单位/参考范围/标记`，而说明文字与解析器用 6 列
`项目/结果/单位/参考下限/参考上限/标记`。照抄占位符自带示例会错位：

```
输入  肌酐 ⇥ 88.4 ⇥ umol/L ⇥ 41-81 ⇥ ↑     （占位符原样）
解析  参考下限="41-81"  参考上限="↑"  标记=空
后果  ↑ 异常标记丢失，非数值被写入参考区间字段
```

建议让占位符、说明文字与解析器统一为 6 列，或让解析器识别 `41-81` 这类合并区间并自动拆分。

### F3 [低] 新建监控组后导出面板仍说"暂无监控组" — 未修

趋势页创建监控组后，同页导出面板未刷新自己的组列表，需整页刷新才出现。
导出本身仍可用（不勾选即包含全部组），影响有限。

### F4 [低] 导出预览缺口计数与实际列出条数不符 — 未修

预览标题写「10 项数据缺口」，列表只渲染 8 条且无截断提示。未列出的是
URIC_ACID 无数据、BMI 无来源页。缺口清单本身是好设计，计数对不上会削弱可信度。

## 排查后排除

- **导出 PDF 字体不是细体**：PDF 内部 BaseFont 为 `NotoSansSCThin-Regular`，疑似 100 字重、
  影响医生可读性。解析字体表确认 `usWeightClass = 400`、fsSelection 为 REGULAR，
  "Thin" 只是 @fontsource 上游命名残留，真实字重正常。
- **导出"生成后数据有更新"不是误报**：首份导出刚生成即被标记陈旧。连续三次预览哈希一致、
  新建导出 `stale:false`、渲染完成后仍为 `false`；操作账本显示确有另一会话在此期间创建监控组。
  机制正确，反而证明能捕捉并发改动。

## 补充:AI 单据识别专项(同日追加)

初次验收只验了链路通断,未测识别率。补测后结论如下。

### 修复前:真实单据可用识别 0/6

账号内 6 份真实单据(另有 9 份"冒烟-xxx"合成图,全部返回 `unknown` 且字段全空,不计入)。
把模型原始输出与 schema 校验分开观察后发现,**模型识别得很准,结果却被整份丢弃**:

| 单据 | 模型实际读到 | 结局 |
|---|---|---|
| d7twj4 血常规 | 向坤/男/41岁/lab_report(conf 1.0)/龙岗区第二人民医院城市广场社区健康服务中心/全科/2026-08-21 | ✗ 全部丢弃 |
| d5ke69 体检 | checkup_report + 日期 | ✗ 全部丢弃 |
| dhvgmt 合成样张 | 内分泌科 + 2026-08-20 | ✗ 全部丢弃 |
| d24aak 火锅发票 | — | ✗ ```json 围栏致 JSON.parse 失败 |
| dgrk5r 税务单据 | other + ECOVIS Hannover Steuerberater | ✓ |
| dqqb33 | 全空 | ✓ |

规律很刺眼:**模型读得越好,越容易被丢弃**。读出时刻的全废,读成空的反而通过。

### 三个根因(均在输出处理,不在模型)

1. **`event_at` 强制时区偏移**。`IsoDateTime = z.string().datetime({ offset: true })`,
   而单据上印的是「19:08」这种无时区墙上时间,模型如实转录反被判非法。整份 payload 因此作废。
   讽刺的是写库处的 `event_time_source` 取值本就叫 `s1_unspecified`——代码早就预期它没有时区。
2. **```json 围栏**。即使指定了 json_schema,模型偶尔仍把 JSON 包在 markdown 围栏里,`JSON.parse` 直接失败。
3. **诊断信息被丢弃**。`S1Error` 把具体字段错误存进 `detail`,handler 只取 `e.message`,
   账本里只剩一句"输出未通过 schema 校验",事后无从复盘。

### 修复(`f882023`)

- 新增 `Stage1OutLenient` 作为**响应解析层**:接受带/不带偏移两种时刻,日期不合规仅该字段退化为 null。
- **线上契约 `Stage1Out` 一字未动**——它同时是发给模型的 json_schema 与 artifact 存储类型,
  改它会让请求指纹漂移、4 份既有 cassette 基线全部失配。
- handler 按**档案所有者时区**把无偏移时刻定成瞬时后再交给严格层。
  直接 `new Date(naive)` 会按进程本地时区(容器内为 UTC)解释,深圳单据凭空平移 8 小时。
- 分批合并路径 `stage1-merge` 同步改用宽松层,否则多页文档仍在合并时整份丢弃。
- 保留 `S1Error.detail` 进账本。
- 新增 `apps/api/test/s1-event-time.test.ts`:时区换算(含夏令时、跨零点)、单字段容错、
  以及"线上契约必须保持严格"的回归锁。

### 遗留:供应商拉取预签名图失败

`DeepSeek Responses 400: Failed to download image from https://s3.medireco.eckstein.pro/...`

架构是把预签名 URL 交给供应商自行下载。该失败**与图片大小相关但不确定**:
d7twj4(1.1 MiB)曾失败、重试第 2 次成功;d5ke69(962 KiB)重试 5 次全败;
≤705 KiB 的从未失败。判断为跨境拉取的稳定性问题,而非硬性尺寸上限。

**已解决(`3cdeab8`)**——而且不是取舍,是纯赚。

owner 提示 DeepSeek 会自动缩图后实测确认:`deepseek-v4-flash-vision-exp` 把每张图归一到
固定的 384 图像 token。同一份化验单按长边 800 / 1024 / 2576 各跑多轮,**`input_tokens` 恒为 2002**
——2576 那张 903 KiB 的图一个 token 都没多买,却在两处付出代价:

| 长边 | 体积 | 成功率 | 姓名识别 |
|---|---|---|---|
| 800 | 123 KiB | 3/4 | 1 次误读「向华」 |
| 1024 | 205 KiB | 3/4 | 全部正确 |
| 2576(原值) | 903 KiB | **1/4** | 唯一一次成功误读为「肖坤」 |

- 可靠性:2576 的失败几乎都是供应商跨境回拉 903 KiB 对象超时。
- 准确度:姓名要喂 `personCheckOf` 做归人对账,误读会直接产出**假的 person_check mismatch**。
  让 sharp 用 Lanczos 缩到接近模型原生尺寸,好过把大图丢给供应商自己压。

`DERIVATIVE_SPEC.ai` 由 `maxEdge 2576` 改为 **1024**(768×1024 ≈ 79 万像素,略高于该模型
约 800×800 的目标像素量,给小字留余量)。原注释写的 "2576 是 Opus 5 高分辨率档"——参数
一直是按一个我们没在用的供应商选的。该值已标注为**随供应商而定,换供应商必须重测**。

删除旧 `ai-01.webp` 令其按新规格惰性重生成(`derived/exports/` 下的导出件未动)。
重跑后 **6/6 全部 attempt 0 一次通过**,含此前 5 次重试全败的 d5ke69,其模型输入由 962 KiB 降至 181 KiB。

注:实验中出现的 JSON 截断是我把 max_tokens 设成 8000 所致,生产为 16000,非生产问题。
