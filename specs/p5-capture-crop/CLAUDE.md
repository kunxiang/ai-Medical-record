# P5 · 采集端人工确认的裁切

## 用户目标

- 拍照后自动做形状调整再送识别，且**人可以在这一步参与修正是否正确**。
- 不牺牲「原件是唯一真相」：归档件一个字节都不能变。

## 当前工作

- **阶段**: 已发布到部署实例；实例已全量重置，等待新的对照素材
- **下一步**: 待 owner 上传新的真实单据后，跑裁 / 不裁对照，量姓名与数值字段的准确率
- **阻塞**: **有** — 对照素材缺失。2026-08-31 的全量重置删除了 8-30 那 6 份真实单据的
  S3 原件（owner 授权，确认为纯测试数据）。快照 `amr-before-reset-20260831-0624.sql.gz`
  只保留数据库行（含当时的提取结果），**不含图像字节**，无法重跑。基准必须用新素材重建。

## 关键决策

见 [ADR-052](../../docs/adr.md)。核心取舍：**存的是四个角点，不是第二张校准图。**

项目所有者提议「一个原图 + 一个校准图」两个存档，这消解了自动裁切最大的两个反对意见
（无不可逆销毁、人在场无静默劣化）。但两个存档的形态代价被低估——新增 L1 图像对象
要在权威矩阵登记、上 ≥10 年锁、打包必带、体积翻倍，还引出 ADR-001 回答不了的
「复核该看哪张」。关键在于人产出的不是图而是四个点，校准图是它们的确定性函数。

不做透视矫正的硬理由：sharp 0.33.5 的几何操作只有 `affine/extract/rotate/resize/trim`，
`affine` 是 2×2 线性矩阵，数学上做不了投影变换。轴对齐裁切零新增服务端依赖，
透视矫正则强制再引一套 OpenCV 或 ImageMagick。

## 三条不可改的约定

1. **角点坐标系 = 按 EXIF Orientation 旋正之后**，归一化到 [0,1]，顺序左上/右上/右下/左下。
   采集端量尺寸用 `imageOrientation:'none'`，服务端第一步是 `.rotate()`——记错坐标系会让
   Orientation=6 的照片整体转 90°、裁出一条边**且不报错**。
2. **渲染顺序恒为 `.rotate()` → `extract` → `resize`。** 裁切放到 resize 之后等于白做。
3. **`capture.json` 读接受 2.0/2.1，写只在真有裁切时才升 2.1。** `putWormIdempotent` 做
   逐字节比对且不一致即抛错，无条件升版会让跨部署的续跑上传炸掉。

## 已知未解

- **对折单据**：折痕是强直边，可能只框住半页，而半页的面积占比与长宽比都还在闸门的
  合理区间内，缩略图也看不出来。三道闸门全拦不住，只能靠人工在预览里发现。
  第一批人工调整数据要专门统计有折痕单据的改框比例。
- **收益未证明**：合成图上裁与不裁识别结果完全一致（字号偏大，26% 占比下也认得出）。
