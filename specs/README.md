# Specs

工程侧的实现规范。与设计文档(docs/)的关系:**设计回答为什么,spec 回答做出来的东西怎么判对错。** 流程见 [docs/10 · 开发流程](../docs/10-dev-process.md)。

## 规范性语言

| 词 | 语义(RFC 2119) |
|---|---|
| **必须** | MUST —— 违反即实现错误 |
| **禁止** | MUST NOT |
| **应当** | SHOULD —— 偏离需在代码注释处说明理由 |
| **可以** | MAY |

## 硬约定

1. **每条验收项可执行**:命令或断言,有明确的通过/失败判据。
2. **留白显式化**:未决定之处标 `[欠定]`,由 spec 审核裁决;禁止隐式含糊。
3. **偏差显式化**:与设计文档不一致处标 `[偏差:vs 文档 §节]` 并给理由。
4. **spec 冻结**:里程碑开工后,spec 改动等同设计改动 —— 记录在该里程碑目录的 `CHANGES.md`,重大者走 ADR。

## Spec 审核 checklist(审核员用)

- **歧义**:同一句条文,两个合理实现者会做出不同东西吗?
- **欠定**:实现者会在哪里被迫自己做决定?(枚举值、边界、错误行为、并发、时区、编码)
- **设计偏差**:逐条核对引用的设计文档章节与 ADR,spec 是否忠实?未标注的偏差 = A 档 blocker。
- **不可测验收**:99-acceptance 里有跑不出通过/失败的条目吗?
- **边界泄漏**:spec 是否偷偷做了属于后续里程碑的决定?或依赖了后续里程碑才存在的东西?
