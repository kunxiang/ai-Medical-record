# 05 · 采集与情境问答

## 0. 设计原则

| 原则 | 含义 |
|---|---|
| **拍照到入库 < 10 秒** | 摩擦一旦超过阈值,人就不会坚持,档案就有缺口 |
| **确认发生在使用时,不在录入时** | 唯一例外:归人 |
| **只在现场问会过期的** | 其余推迟到晚上 |
| **能点的别让人说** | 语音只用于开放性问题 |
| **跳过零成本** | 否则用户会为了逃避问答而不拍照 |

## 1. 采集流程

```
① 拍照 / 选图 / 导入 PDF(界面常驻人员选择器,默认上次选的人)
      ↓  (立即写入 IndexedDB —— 此刻已算"存档成功")
② ★ 归人确认 —— 本地手选,唯一强制的即时确认(离线可用)
      ↓
③ 现场问答(3–5 题,可全部跳过)
      ↓
④ 后台上传 + AI 识别元数据 + 归人对账(AI 读名与所选人比对,不一致才提醒)
      ↓
⑤ 当晚推送:补录医嘱与用药
```

### 输入形态

必须**从第一版就支持多种输入**,不能只有相机:

| 来源 | 场景 |
|---|---|
| 相机(连拍模式) | 纸质单据。多页报告需要连续拍摄不退出 |
| 相册 | 之前拍的、别人发来的 |
| PDF | 医院 App / 公众号导出的电子报告 |
| 截图 | 自助机界面、公众号里的结果页 |
| 批量导入 | 存量旧单据一次性扫描 |

### ⚠️ 有时效性的抢救工作

**热敏纸会褪色。** 很多医院的化验单是热敏打印,一两年就变淡甚至空白。这让"第一时间拍照"从好习惯变成**抢救**。

**建议在系统可用后立刻做的事:**

1. 把家里现存的旧单据集中扫描一批,**越老的越优先**
2. 如果拿到过 CT/MRI 的 DICOM 光盘,**趁还有读盘设备赶紧导出** —— 再过几年那些盘等于不存在
3. 影像:**拍胶片基本无用**(信息在报告文字里),优先拍报告

## 2. 归人确认(唯一的强制环节)

### 为什么只有这一步不能延后

归错人会同时污染两个人的档案 —— 把父亲的肌酐画进你的趋势线 —— 而且:

- **没有任何自洽校验能发现它**(数值本身完全合理)
- 数值错了有算术校验兜底、有原图可查;**归人错了是静默的、会长期潜伏的污染**

所以它是**唯一**在录入时必须人工确认的字段。

### 流程([ADR-041](./adr.md#adr-041) 修订:本地手选在前,AI 事后对账)

```
拍照界面常驻人员选择器(默认 = 上次选的人)
      ↓
用户点选归属人(1 次点击,离线可用,无需 AI)
      ↓
入队上传(S3 key 由所选 person 决定)
      ↓
服务端 AI 提取后,从影像读姓名/证件号 ──> 与所选 person 比对
      ↓
  ┌───────────────┴───────────────────┐
一致(绝大多数)                  不一致 / 读不出
  ↓                                   ↓
静默通过,不打扰                document.person_mismatch = true
                                进入归人对账队列(07 §归人对账)
                                用户裁决:改归属 或 确认 AI 读错
```

为什么翻转为"本地手选在前"而不是"AI 建议在前":

- **拍照时用户就站在诊室里,心里清楚这是谁的单子** —— 此刻点一下的成本最低、准确率最高
- AI 建议要等上传+提取完成,**离线队列里的文档会卡在"待归人"状态**,与"拍完即存档成功"冲突
- AI 从此变成**对账者而非决策者**:它的读名结果只用于事后核对,发现不一致才打扰用户

**永远不允许无人工归属的文档静默入库。** 批量导入是唯一例外(`status = needs_person_confirm`,见 07)。

### AI 对账时的匹配信号(按可靠性排序)

1. `person_identifier` 院内就诊卡号/病历号/登记号命中 —— 最可靠
2. 姓名 + 出生日期 同时命中
3. 姓名 + 性别 + 年龄段
4. 仅姓名 —— **家里有同姓亲属时不可信**,只作弱信号

## 3. 引导式问答

### 3.1 分层:按"过期速度"划分

| 时机 | 题量 | 问什么 | 为什么必须在这时 |
|---|---|---|---|
| **现场(拍完立即)** | 3–5 | 空腹?几点抽血?今天为什么来?最近哪不舒服? | 几小时后记不清,几天后彻底丢失 |
| **当天晚上(推送提醒)** | 3–5 | 医生说了什么?开了什么药?下次何时复查? | 当天还记得,不占用现场时间 |
| **随时可补** | 不限 | 长期用药清单(拍药盒)、既往史 | 不依赖记忆 |

在医院你实际只有 60–90 秒。**现场问的每一题都要能证明它"过期作废"。**

### 3.2 交互:点击优先,语音兜底

| 答案形态 | 控件 | 例 |
|---|---|---|
| 二选一 / 少量选项 | **按钮** | 空腹 / 非空腹 |
| 时间 | 时间选择器 | 抽血时间 |
| 是否 | 开关 | 近期是否发热 |
| 开放叙述 | **按住说话** | 症状描述、医生说了什么 |

一次典型采集:**点 3 下 + 说 2 句**。

### 3.3 录音规则

- **按问题分段录音**,不是一整条。每段音频原子性地绑定到一个问题
  - 好处:可单独重答某题、可跳过、转写失败只影响一题
- **原始音频永不删除**,与影像同级(见 [04 · 存储布局](./04-storage-layout.md#1-key-布局))
- 转写与结构化是可重跑的派生层,记录 `transcript_model` 与 `transcript_version`
- **必须可跳过、可中断、可续答** —— 在医院大厅对着手机说病情,很多时候不方便

### 3.4 AI 追问

允许 AI 基于回答追问,但**最多 1–2 轮**,否则会变成没完没了的对话。追问也记入 `context_answer`,`question_key` 前缀 `followup_`。

## 4. 问答模板

模板按 `doc_type` 分支,**文件版本化**(`templates/lab-report.v1.json`),`context_session` 记录用的是哪一版。

### 4.1 化验单 · 现场(`lab-report.v1` · onsite)

| # | key | 问题 | 类型 | 选项 |
|---|---|---|---|---|
| 1 | `fasting_status` | 这次抽血是空腹吗? | choice | 空腹(≥8h) / 非空腹 / 不确定 |
| 2 | `collection_time` | 大概几点抽的血? | datetime | 默认当前时间 |
| 3 | `visit_reason` | 今天为什么来医院? | audio + text | — |
| 4 | `current_symptoms` | 最近有什么不舒服吗? | audio + text | 可跳过 |
| 5 | `recent_illness` | 最近两周有没有发热、感染、剧烈运动? | multi_choice | 发热 / 感染 / 剧烈运动 / 都没有 |

> 第 5 题对应**分析前变异**:急性期反应会让铁蛋白↑、白蛋白↓、血脂**假性降低**;剧烈运动会让 CK、AST、肌酐显著升高。详见 [08 · 医学参考层](./08-medical-reference.md#3-分析前变异)。

### 4.2 化验单 · 当天补录

| # | key | 问题 | 类型 |
|---|---|---|---|
| 6 | `doctor_advice` | 医生说了什么? | audio |
| 7 | `medication_changes` | 有没有开新药或调整用药? | audio + 拍药盒 |
| 8 | `followup_plan` | 下次什么时候复查? | date / text |

> 第 6 题的价值常被低估 —— **口头医嘱经常不写在任何单子上**,而它往往是最重要的信息。

### 4.3 影像报告(`imaging-report.v1`)

| key | 问题 | 类型 |
|---|---|---|
| `exam_reason` | 为什么做这个检查? | audio + text |
| `contrast_used` | 有没有打造影剂? | choice |
| `prior_comparison` | 报告里有没有和以前的片子对比? | choice |
| `doctor_advice` | 医生怎么解读的? | audio |

### 4.4 处方 / 用药(`prescription.v1`)

| key | 问题 | 类型 |
|---|---|---|
| `is_new_medication` | 是新开的药还是续方? | choice |
| `indication` | 针对什么问题开的? | audio + text |
| `duration` | 计划吃多久? | text |
| `prior_med_stopped` | 有没有停掉哪个药? | audio |

### 4.5 体检报告(`checkup-report.v1`)

体检报告是**合集**,单独处理:

| key | 问题 | 类型 |
|---|---|---|
| `checkup_type` | 单位体检 / 自费体检 / 入职体检? | choice |
| `fasting_status` | 抽血时是空腹吗? | choice |
| `abnormal_noted` | 报告里标了哪些异常?(可跳过,AI 会提取) | audio |

### 4.6 通用兜底(`generic.v1`)

类型识别失败时使用:

| key | 问题 | 类型 |
|---|---|---|
| `what_is_this` | 这是什么单子? | audio + text |
| `visit_reason` | 当时为什么去的? | audio + text |

### 4.7 女性专项(可选,按 person 配置)

对育龄女性,化验单模板追加一题 —— 月经周期影响血红蛋白、铁蛋白、部分激素:

| key | 问题 | 类型 |
|---|---|---|
| `menstrual_phase` | 目前处于月经周期的哪个阶段? | choice(月经期 / 卵泡期 / 黄体期 / 不确定 / 不适用) |

## 5. 模板 Schema

```json
{
  "template_id": "lab-report",
  "version": "1",
  "doc_types": ["lab_report"],
  "stages": {
    "onsite": {
      "max_questions": 5,
      "questions": [
        {
          "key": "fasting_status",
          "text": "这次抽血是空腹吗?",
          "type": "choice",
          "options": [
            { "value": "fasting",     "label": "空腹(≥8小时)" },
            { "value": "non_fasting", "label": "没空腹" },
            { "value": "unknown",     "label": "不确定" }
          ],
          "skippable": true,
          "maps_to": "observation_context.fasting"
        },
        {
          "key": "visit_reason",
          "text": "今天为什么来医院?",
          "type": "audio",
          "allow_text_fallback": true,
          "skippable": true,
          "max_duration_ms": 60000,
          "maps_to": "encounter.chief_complaint"
        }
      ]
    },
    "same_day": { "questions": [ "…" ] }
  },
  "conditional": [
    {
      "when": { "person.sex_at_birth": "female", "person.age_between": [12, 55] },
      "append_to": "onsite",
      "questions": [ { "key": "menstrual_phase", "…": "…" } ]
    }
  ]
}
```

**`maps_to`** 指明这个回答最终写进哪个字段,让问答与数据模型解耦。

## 6. 移动端实现要点

### 拍照

```html
<input type="file" accept="image/*" capture="environment" multiple />
```

- 多页报告需要**连续拍摄模式**:拍一张 → 缩略图入列 → 继续拍,不退出
- 上传前只做 EXIF 方向校正,**不做有损压缩**
- 从 EXIF 读 `DateTimeOriginal` 作为 `captured_at`

### 录音

- `MediaRecorder` API,iOS Safari 14.3+ 支持
- iOS 首次需**用户手势**触发麦克风权限 —— "按住说话"的 `touchstart` 满足条件
- 格式:优先 `audio/mp4`(iOS)/ `audio/webm`(Android),服务端统一转 `m4a` 归档
- 按住时长 < 500ms 视为误触,不产生记录

### 离线队列

```
拍照 ──> IndexedDB(原图 blob + 元数据 + 问答)
            ↓
       上传队列(前台驱动:前台化 / online / 定时扫描,ADR-046)
            ↓
       预签名 URL 分片上传 ──失败──> 指数退避重试
            ↓
       服务端确认 ──> 清理本地 blob
```

**UI 必须显示队列状态**(「3 张待上传」),让用户敢离开医院。

⚠️ 但**不得**承诺"关掉也会传":iOS 无 Background Sync,队列只在应用打开时推进(ADR-046)。文案必须如实,否则用户会在错误的信任下离开。

### 未来平台的可移植性

| 部分 | 可移植 |
|---|---|
| 问答模板(JSON) | ✅ |
| 数据模型与 API 契约 | ✅ |
| 医学计算 | ✅ |
| **离线队列** | ❌ 小程序无 Service Worker,存储 API 不同,必然重写 |
| 相机/录音调用 | ❌ 各平台 API 不同 |

提前认清这一点,不要为了"统一"而设计一个谁都不好用的抽象层。
