# 架构决策记录(ADR)

记录关键决策及其**理由**。理由比结论重要 —— 几年后回看时,需要知道当初在权衡什么,以及什么条件变化会让决策失效。

格式:决策 / 背景 / 后果 / 何时应重新考虑。

---

## ADR-001 · 原始影像是唯一真相来源

**决策:** 原始影像与音频不可变、永久保存;AI 提取出的一切都是可再生的派生层。

**背景:** 最初的设想是"OCR 错误必须在录入时人工确认"。但那把提取当成一次性、不可逆的动作。一旦确立"影像即真相",提取错了随时能重跑,这个前提就不成立了。

**后果:**

- 提取层必须**版本化**(记录 model + prompt version + pipeline version)
- 确认可以延后到**使用时**,而不是录入时 —— 这让录入能压到几秒
- 数据库与索引都成为**可从 S3 重建的缓存**
- 未来模型变强,整个档案自动变准

**何时重新考虑:** 如果存储成本变得不可忽略(目前每年 < 1GB,不会发生)。

---

## ADR-002 · 归人是唯一在录入时强制确认的字段

**决策:** 所有确认延后到使用时,**除了文档归属于哪个人**。

**背景:** 归错人会同时污染两个人的档案,而且:

- **没有任何自洽校验能发现它** —— 数值本身完全合理
- 数值错了有算术校验兜底、有原图可查;归人错了是静默的、会长期潜伏的污染

**后果:**

- `POST /documents` 必须带 `person_confirmed: true`,否则 400
- AI 只给建议,永不自动归人,哪怕置信度 0.99
- 归人纠正走独立接口并记 `audit_log`

**何时重新考虑:** 不会。这是数据完整性的底线。

---

## ADR-003 · 人工投入放在情境,不放在数值

**决策:** 不让人敲数字(可从影像再生),让人花 30 秒记情境(不可再生)。

**背景:** 影像里有的信息以后都能重新提取;影像里**没有**的信息只有当时能记录 —— 为什么去看病、是否空腹、几点抽血、在吃什么药、医生说了什么。

**后果:**

- 引导式问答成为**唯一真正需要人的环节**
- 问答按"过期速度"分层:现场必答 / 当天补 / 随时补
- 语音是最低摩擦的形式,但只用于开放性问题;能点的用按钮

**何时重新考虑:** 如果出现能可靠还原就诊情境的技术(不太可能)。

---

## ADR-004 · 引导式分话题问答,而非自由录音

**决策:** 文字提问 + 按住说话,一题一段音频;不做一整条自由录音。

**背景:** 开放式录音信息密度极低,会说一大堆废话,而且必然遗漏重点。

**后果:**

- 问题模板需**版本化**(两年后要知道当时问的是哪一版的哪一题)
- 按问题分段录音 → 可单独重答、可跳过、转写失败只影响一题
- 必须可跳过、可中断、可续答 —— 否则用户会为了逃避问答而不拍照
- AI 追问设 1–2 轮上限

**何时重新考虑:** 若实测显示自由录音 + AI 结构化的效果超过引导式问答。

---

## ADR-005 · 音频与影像同级,原始录音永不删除

> ⚠️ **部分修订于 ADR-045**:转写从音频 sidecar 分离,落 `derived/.../transcripts/`(可重跑,L1 零字节变动);音频 sidecar 只存事实。

**决策:** 原始音频归档到 S3,与影像同等地位;转写是可重跑的派生层。

**背景:** 与 ADR-001 同源。今天的 ASR 认不出的方言或医学术语,以后能认出来。

**后果:** `context_answer` 同时存 `audio_key`、`transcript`、`transcript_model`、`transcript_version`。

## ADR-006 · 参考区间跟着每条数值走

**决策:** 不在系统里定义全局"正常范围";每条 observation 携带该次报告自带的参考区间。

**背景:** 不同医院用不同仪器、试剂、方法学,参考区间本身就不同。同样的 ALT 45 U/L,在上限 40 的实验室是 ↑,在上限 50 的实验室是正常。

**实证强化(用例 004):** 原本的论据是「不同医院参考区间不同」。真实数据给出了强得多的版本 —— **同一家医院、同一台 BC-7500-2、同一个 3 岁 0 月的孩子、相隔 7 天,27 项中 14 项参考区间不同**(WBC 4.90–12.70 → 4.40–11.90;Hb 115–150 → 112–149;LYMPH% 26–67 → 23–69)。年龄未跨段。原因可能是标本类型切换或实验室更新区间库,**从单据无法判定 —— 但工程要求与原因无关**。

**后果:**

- `observation` 有 `ref_low` / `ref_high` / `ref_text` / `ref_source`
- 趋势图上不同来源的参考区间需分别标注
- **任何形式的参考区间缓存、复用、跨报告继承都是错的**
- `packages/medical` 里的区间数据**仅用于量级校验与展示上下文**,绝不用于判定异常

**何时重新考虑:** 不会。做错这条,系统的可信度归零。

---

## ADR-007 · 呈现数据,不给结论

**决策:** 系统不做诊断、不判定正常/异常、不给建议。

**背景:** 一旦页面上出现「AI 提示您可能存在胰岛素抵抗」,医生对整份材料的信任度会下降,而且带来不必要的心理与法律负担。项目的目标本来就是**给医生提供佐证**,不是自我诊断。

**后果:**

- 允许中性的数据性陈述:「本次变化超出常规生物学波动」「该次为非空腹」
- 诊断阈值可作为**明确标注来源的参考线**出现,但系统不渲染结论
- 导出的 PDF 不含任何 AI 解读

**何时重新考虑:** 不会。

---

## ADR-008 · S3 兼容对象存储 + 人类可读 key

> ⚠️ **部分修订于 ADR-041**:key 中的 facility/doctype/日期语义已移除(它们是上传后 AI 才知道的),可读性由 sidecar 与 `_index/views/` 承担;对象锁改治理模式。
> ⚠️ **再修订于 ADR-045**:sidecar 一分为二 —— `capture.json`(拍摄事实,WORM)+ `derived/.../meta.json`(AI 观点,可重写);extractions 迁出档案区;views 迁至 `derived/_views/`。

**决策:** 原件存 S3,key 结构人类可读,配套 sidecar JSON;数据库只作索引。

**背景:** 档案要活得比应用久。五年后代码可能烂了,但用任何 S3 客户端应该仍能看懂里面是什么。

**后果:**

- key 形如 `people/p3f7a2/2024/2024-03-15__xiehe__lab_report__d7k2m9/`
- 每个对象旁有 sidecar JSON;`_index/` 下有映射表与月度清单
- 必须能从 S3 完全重建数据库(`tools/rebuild-index`)
- 建桶时开启 versioning 与 object lock(**事后无法补**)

## ADR-009 · key 用 ASCII,可读性靠 sidecar 补偿

**决策:** S3 key 只用 ASCII slug;中文名放在 sidecar 与索引文件里。

**背景:** S3 支持 UTF-8 key,中文更直观。但部分 SDK/CDN 对非 ASCII key 的签名与 URL 编码有坑,受限环境(如小程序)兼容性不确定,跨系统迁移时转义麻烦。

**后果:**

- `person_slug`、`doc_short_id`、`facility_slug` 都是 ASCII,生成后永不更改
- `_index/people.json`、`_person.json`、`document.json` 提供中文映射
- 浏览时 `rclone cat` 读一下 JSON 就知道是什么

**何时重新考虑:** 若确认所有目标平台对 UTF-8 key 支持无虞,且更看重直接浏览体验。

---

## ADR-010 · 主存储 + 第二处备份

**决策:** S3 为主,定期 rclone 同步到第二处(另一家云或 NAS)。

**背景:** 云比家里的硬盘可靠得多,但云挂掉的方式通常是**欠费停服、账号异常、服务商变更、误删**,而不是磁盘故障。对一份存几十年的档案,这是单点。

**后果:** 每日增量同步 + 每月完整性校验 + 半年恢复演练。成本极低,一条 cron 就够。

---

## ADR-011 · 单账号多档案,但结构上为多用户预留

**决策:** 用 `person_access` 关联表,而不是把 `person` 直接挂在 `account` 下。

**背景:** 事后给已有表加租户键是代价最高的迁移之一;而多加一张两列的关联表,今天几乎零成本。它同时顺手解决了"夫妻共同管理孩子档案"这类真实需求。

**后果:**

- 所有查询从第一天起就经过 `person_access` 过滤 —— 留一个能绕过它的路径,就是留一个未来的越权漏洞
- 业务表带 `person_id` 而非 `account_id` —— person 才是数据的归属主体
- Day 1 只有 N 行数据,但结构对了

---

## ADR-012 · API-first,客户端只做采集与展示

**决策:** 全部业务逻辑在服务端;客户端是薄壳。

**背景:** 两个约束指向同一方向 ——(1)AI 密钥绝不能进前端;(2)未来要支持 App 与小程序。

**后果:**

- 换平台时只需重写一层壳
- `packages/contracts` 是接口的唯一真相,不允许在 app 里手写"差不多"的类型
- `packages/medical` 保持**零依赖纯函数**,才能在浏览器/Node/小程序里原样跑

## ADR-013 · 离线优先是 P0,不是优化项

> ⚠️ **实现手段修订于 ADR-046**:Service Worker 后台重试在 iOS 上不可实现(无 Background Sync,且 SW 读不到 token)→ 改为**前台驱动**。「离线优先是 P0」的决策本身不变。

**决策:** 第一版就做 IndexedDB 队列 + Service Worker 后台重试。

**背景:** 医院网络普遍很差(地下室检验科、人多的门诊楼)。**如果拍照后上传失败就丢了,系统在最关键的场景下失效,用户会失去信任并停止使用。**

**后果:**

- 技术选型被迫是 PWA,不是普通网页
- 写入本地即视为"已存档",UI 立刻给正反馈
- 队列状态必须可见,让用户敢离开医院
- `client_document_id` 幂等键是必需的,否则重试会产生重复文档
- 小程序无 Service Worker,这部分代码天然不可移植 —— **提前认清,不要为了"统一"而设计一个谁都不好用的抽象**

## ADR-014 · 归档管道与提取管道解耦

**决策:** AI 失败不阻塞归档。原件照常入库,`doc_type = unknown`,`full_text` 留空。

**背景:** ADR-001 的直接推论 —— 既然影像是真相、提取可重跑,就没有理由让提取失败挡住归档。

**后果:** AI 挂了、额度用尽了、模型下线了 —— 拍照存档照常工作。这是系统韧性的核心。

---

## ADR-015 · 全文索引的源是 AI 读出的完整文本

**决策:** 除结构化字段外,必须保存并索引 `extraction.full_text`。

**背景:** **结构化提取会失败,全文不会。** 哪怕表格解析全错,只要文本在索引里,就还能找到那份单据。

**后果:** 这是档案系统的兜底能力,不是可选优化。语义检索建立在其之上。

---

## ADR-016 · 算术自洽校验用纯代码,不用 AI

**决策:** 单位换算与自洽校验是确定性代码,不交给模型。

**背景:** 让模型做算术是引入错误,不是消除错误。而化验单内部本身有冗余关系(白细胞分类和 ≈ 100%、总蛋白 = 白蛋白 + 球蛋白等),可以免费查错 —— **小数点错一位,这些等式立刻崩掉**。

**后果:**

- 规则实现在 `packages/medical/src/consistency/`,单元测试覆盖率要求最高
- 这是抓 OCR 错误性价比最高的手段
- **目标不是零错误,是让错误可见** —— 标出来 + 能一键看原图核对,就够了
- 因此 `source_bbox` 是必需字段,不是可选

## ADR-017 · 人工修正优先于机器提取

**决策:** 重跑提取时,`review_status ∈ (confirmed, corrected)` 的 observation 不被覆盖。

**背景:** 若重跑会抹掉人工修正,用户就再也不敢修正了。

**后果:** 重跑工具必须实现这条保护;差异生成报告供人工抽查。

## ADR-018 · 三个日期分开存

**决策:** `sampled_on`(采样)/ `reported_on`(报告)/ `encounter.occurred_on`(就诊)独立存储。

**背景:** 三者经常差好几天。**做趋势用采样日期,找档案时人记得的往往是就诊日期。**

**后果:** 存的时候就分开,以后无法补救。检索接口提供 `date_field` 参数选择按哪个日期筛。

---

## ADR-019 · 血压走独立数据流

**决策:** 血压不从化验单 OCR;走手动录入,并用 `measurement_setting` 区分诊室/家庭/动态。

**背景:** 诊室血压有白大衣效应,单次值噪声很大;而且不同测量方式的诊断阈值不同(诊室 ≥140/90,家庭自测 ≥135/85,动态 24h ≥130/80)。**不同 setting 的数据不能画在同一条趋势线上。**

**后果:** 血压是唯一一个与其他指标数据流不同的监控项,一开始就分开设计。

---

## ADR-020 · 派生指标必须记录公式版本

**决策:** eGFR 等派生值存 `derived_formula`(如 `CKD-EPI-2021`)。

**背景:** eGFR 用 CKD-EPI 2021 还是旧的 MDRD,结果不同。不记版本则前后不可比。

**后果:**

- `person.birth_date` 与 `sex_at_birth` 成为**必填字段** —— 公式需要它们
- 儿童应拒绝计算成人公式,而非给出错误值

---

## ADR-021 · TypeScript 全栈

**决策:** 前后端统一 TypeScript,而非 Python 后端。

**背景:** 本项目只调用 AI 的 HTTP API,不训练模型,Python 的 AI 生态优势用不上;而前后端共享类型契约是多平台策略的核心。

**后果:** `packages/contracts` 与 `packages/medical` 可被所有客户端直接复用。

**何时重新考虑:** 若未来需要本地模型推理或重度数据科学计算。

---

## ADR-022 · 服务端加密而非客户端加密

**决策:** 使用 S3 服务端加密(SSE),不做客户端加密。

**背景:** 客户端加密后服务端拿不到明文 → 无法生成缩略图、无法 OCR、无法建全文索引与语义检索。**所有智能都得搬到客户端。**

**后果:** 这是**功能与隐私的取舍**,由项目所有者判断。此处只记录代价。

**何时重新考虑:** 若隐私要求变化,或客户端算力足以承担全部处理。

---

## ADR-023 · observation 的唯一性由 `concept_code + qualifier` 决定

**决策:** 增加 `qualifier` 字段;同一份报告里同名指标的多个变体分别成行,不合并。

**背景:** 来自[真实用例 001](../fixtures/001-pediatric-emergency/case.md)。血气报告同时给出「氧分压 65」与「氧分压(校正) 67」,**参考区间还不一样**(83–108 / 80–100);pH、二氧化碳分压同理。若都映射到同一个 `concept_code`,趋势图上会出现同一时刻两个点。

**后果:**

- 唯一性由 `(document_id, concept_code, qualifier)` 决定
- 提取 prompt 必须明确"同名行不可去重"
- 趋势查询需指定 qualifier,或默认取未校正值

## ADR-024 · 记录检测仪器,趋势按仪器区分

**决策:** `observation` 增加 `device` 与 `result_kind`;趋势按仪器分组或标注,实测值优先于计算值。

**背景:** 同一用例中,一次采血(17:07)上了两台仪器,同一指标给出不同值:

| | 血气 iSTAT1-300G | 血常规 BC-7500-2 |
|---|---|---|
| 血红蛋白 | 12.60 g/dL = 126 g/L | 130 g/L |
| 红细胞比容 | 37 % | 38.1 % |

两个数都对 —— iSTAT 按 `Hb = HCT × 0.34` 推算(实测 37×0.34 = 12.58 ✓),血球仪比色法实测。**若天真地归一到 g/L 画进同一条趋势线,会出现"同一天两个血红蛋白值"。**

**后果:**

- `result_kind` 区分 `measured` / `calculated` / `input_parameter`
- 输入参数(血气仪的体温、吸氧浓度)不进趋势
- 新增 `cross_device_agreement` 校验规则,偏差 > 10% 才标记(3% 属正常方法学差异)
- **这条规则的真正价值是抓单位换算错误** —— 若一边 126 一边 1300,立刻暴露

**何时重新考虑:** 不会。这是真实世界的物理事实,不是可以设计掉的复杂度。

## ADR-025 · 页序从页脚解析,不依赖拍摄顺序

> ⚠️ **边界修订于 ADR-047**:S3 key 中的 `page-NN` 恒为**拍摄序**(上传瞬间即须确定、永不改名);本 ADR 的页脚解析结果落在 DB 的 `page_no`,二者自 M2 起允许分离。

**决策:** `document_page.page_no` 从页脚「第 N 页,共 M 页」解析;拍摄顺序另存 `capture_order`。

**背景:** 同一用例中,**第 2 页先被拍到**(纸是折叠的)。而多页报告的项目编号**跨页连续**(第 1 页 NO 1–20,第 2 页 NO 21–27)—— 顺序错了,提取结果会错乱。

**后果:** Stage 1 额外产出 `page_label` / `page_no` / `page_total`;Stage 2 之前按 `page_no` 重排再合并提取。

## ADR-026 · 报告编号作为幂等键

**决策:** 新增 `document.report_no`,唯一约束 `(facility_id, report_no)`。

**背景:** 中国医院报告普遍印有唯一报告编号(用例中两份报告编号相邻:…634 / …635)。**这比 sha256 更适合做去重键** —— 同一份单据重拍一张照片,sha256 就变了,报告编号不变。

**后果:** 重复上传自动识别为同一文档,提示用户"这份已存档"。sha256 仍保留用于完整性校验,但不承担去重职责。

## ADR-027 · 叙述型报告独立建表

**决策:** 新增 `report_narrative`(1:1 挂 document),承载 `findings_text` / `conclusions[]` / `recommendation`;结论逐条原文保留,不改写不归一。

**背景:** 化验单是表格 → `observation` 行;影像/病理/出院小结是**叙述文本 + 结论列表**,原数据模型一个字段都装不下。

**后果:**

- `conclusions` 是 jsonb 数组,每条含 `text`(原文)+ `tags` + `laterality`
- 中文影像报告措辞有规范含义:「未见明显异常」≠「正常」。**改写即失真**
- `tags` 是额外加上去用于检索的,原文永远是主体

## ADR-028 · 影像结论的"消失"不等于问题消失

**决策:** 必须记录 `document.exam_items`(检查覆盖范围);纵向对比时若两次覆盖范围不同,**显式标注**;绝不把"未提及"渲染成"已消失"。

**背景:** 真实案例中,2024 年外科门诊专查阴囊(含哭闹诱发)给出两条结论;2026 年急诊主查胃肠道、阴囊顺带,只剩一条。**第二条结论的消失是因为这次没查那一项,不是好转。**

**后果:**

- 不记录覆盖范围,就无法区分「查了没发现」与「根本没查」—— 这两者临床意义天差地别
- 这是影像纵向追踪的头号陷阱,也是 ADR-007(呈现数据不给结论)在影像场景的具体化

**何时重新考虑:** 不会。

## ADR-029 · 影像测量需要解剖部位维度

**决策:** `observation` 增加 `body_site` 与 `value_dimensions`;唯一性扩展为 `(document_id, concept_code, qualifier, body_site)`。

**背景:** 影像测量值是三维的(1.4×0.6×0.9 cm),标量字段装不下;且**左右侧是两条独立时间序列** —— 化验单没有这个概念,影像报告普遍有。

**后果:** 椭球体积公式 `V = 0.5236×L×W×H` 经真实数据验证(算得 0.3958,报告 0.39),因此可给未提供体积的旧报告补算,**让历史数据变得可比**。这是 `is_derived` + `derived_formula` 最有说服力的用例。

## ADR-030 · 输液单是"已执行给药",与处方分开

**决策:** 新增 `doc_type = infusion_order`;`medication.kind` 区分 `prescribed` / `administered`;新增 `administration_group` 承载输液分组。

**背景:** 处方是计划(FHIR `MedicationRequest`),输液单是已执行(`MedicationAdministration`)。输液单特有**分组**结构 —— 同组药物混在同一袋液体里输,共享给药时刻与速度,扁平表装不下。

**后果:**

- `administered_at` 必须精确到分 —— 因为它直接影响后续检验值的解读
- 药物剂量是**另一套单位体系**(体积/质量/浓度混用,mg 与 g 混用),需要独立的 `units/dose` 模块,不可与检验单位混用
- 药名含厂家与集采批次(`5%葡萄糖注射液(科伦250ml,23年集采)`),`name_raw` 存原文,`generic_name` 剥离
- 频次中英混排(`静滴 ONCE 1天`)**不做归一化解析** —— 风险高收益低
- 费用信息**记录但不建模**,存入 `extraction.structured`

## ADR-031 · PII 最小化提取

**决策:** 对档案价值为零、泄露风险高的字段(手机号、身份证号、住址、卡号),AI 识别后**主动丢弃,不写入数据库**。

**背景:** 化验单上没有电话,**输液单上印着家长手机号**。这类字段对长期病历归档毫无价值,却是最敏感的个人信息。

**后果:**

- prompt 中显式列出 `pii_drop_list`
- 回归集加验证用例:**输出里出现手机号即判定失败**
- 原图里当然仍有 —— 但那是不可变原件,不进结构化层、不进全文索引、不进 embedding
- 这与 ADR-022(服务端加密)是不同层面的措施:加密防外部,PII 最小化防内部扩散

## ADR-032 · 跨文档类型的时间轴对齐

**决策:** 新增 `document.event_time` + `event_time_source`;每种 doc_type 定义"最能代表事件发生时刻"的字段。

**背景:** 同一次就诊中,化验单的事件时刻是**采集时间**(17:07),影像是**报告时间**(16:54,实际检查更早),输液单是**打印时间**(18:02)。语义不同,不能直接比大小 —— 但排序后才能还原真实顺序(先超声 → 再抽血 → 再输液)。

**后果:** `event_time_source` 必须记录取自哪个字段,否则时间轴精度无从判断。这是"给药事件与检验值对齐"能力的前提。

## ADR-033 · 单据上的临床诊断是简化标签,不能替代情境问答

**决策:** `clinical_diagnosis` 用于**预填**,情境问答保留"补充/确认"环节。

**背景:** 这是对 ADR 早期判断的**修正**。上一轮从化验单看到「临床诊断:呕吐查因」印在表头,得出"不需要问用户"的结论。但真实情况是:该次就诊主因还包括腹泻,而单据上的诊断是**为开单/计费服务的简化标签**,不是完整临床图景。

**后果:** 问答模板里对应问题从"跳过"改为"预填 + 请补充"。ADR-003(人工投入放在情境)因此更站得住 —— 单据能省掉的只是打字,省不掉判断。

## ADR-034 · 标本类型是趋势的分组维度

**决策:** `observation.specimen` 与 `device` 同级,参与趋势分组;跨标本类型不直接连线、不计算 RCV。

**背景:** 用例 004 与 001 相隔 7 天,同仪器同患者,标本类型不同(末梢血 vs 静脉血):PLT 216 → 417(+93%)、WBC 4.68 → 7.02(+50%)。**末梢血的血小板计数系统性偏低**(采集时血小板聚集黏附)。差异中标本类型贡献多少、真实变化多少,**数据本身分辨不了**。

**后果:** 若天真连线并算 RCV,会得出"变化极显著"的结论,而其中混着系统性偏差。这与 ADR-024(跨仪器)是同一类问题的两个面。

## ADR-035 · 报告的图例不可信,保留原始标记符号

**决策:** 新增 `observation.abnormal_flag_raw` 保留原始符号;标准化 flag 由上下文判断得出,不由符号表查得。

**背景:** 用例 004 的流感单,甲流**阳性**,提示列标 `↑`;而同一张单页脚图例明确印着 `※:阳性`。**单据自己印的规范与自己的用法对不上。**

**后果:** 按图例硬编码映射 → 阳性被漏标。标准化依据应是语义(结果「阳性」+ 参考区间「阴性」→ `A`),而非符号。

## ADR-036 · 列结构不可假设固定

**决策:** 按表头动态解析列,并记录 `document.column_set`。

**背景:** 用例 004 中,同一医院**同一天**的两份报告列数不同 —— 血常规有「单位」「检测仪器」列,COVID 抗原单两列都没有。按固定列序解析必然错位。

## ADR-037 · encounter 归组用时间窗,不用日历日

**决策:** 归组条件为「同人 + 同机构 + `event_time` 落在同一时间窗(如 ±12h)」。就诊内按 `collected_at` 再聚合出"采样事件",不建表。

**背景:** 用例 004 的急诊在**凌晨 05:09**。若某次就诊 23:50 挂号、次日 00:30 抽血,按日历日归组会被拆成两次。

同一次就诊内还有更细的一层:鼻拭子采于 05:09、末梢血采于 05:14 —— **两次采样**。这修正了 ADR 早期的说法:同采集时刻是**采样事件**粒度,不是就诊粒度。

## ADR-038 · 报告自带的解释文本原文保留并标注来源

**决策:** 新增 `document.report_notes` + `report_notes_source = report_original`。

**背景:** 用例 004 的 COVID 单备注栏印着中英双语说明:「阴性结果表示…但不能完全排除感染…需结合临床表现,必要时核酸复查」。这是**报告原文的一部分**,不是系统生成的解读。

**后果:** 必须与系统输出严格区分,避免用户误以为是 AI 的判断。

> 附带印证 ADR-007:连医院自己都在说「不能完全排除」「需结合临床表现」。系统更不该下结论。

## ADR-039 · 提取是校验驱动的多轮闭环,不是一轮

**决策:** 校验失败不是终点,而是"回原图重看"的信号。带着失败详情裁剪相应区域,针对性重读,最多 3 轮。

**背景:** 原设计是单轮提取 → 校验失败 → 标红等人工。但这浪费了一个极强的先验:

> **医院报告是自洽的。不自洽的是我的读法。**

实证:4 个真实用例、**26 次规则执行、零失败**。原因是结构性的 —— MCV、MCH、MCHC、PCT、HCO₃⁻、TCO₂、估算体积**都是仪器自己算出来的**,报告输出前这些等式已经成立。

因此对派生值类校验,`P(OCR 读错) >> P(报告本身错)`。典型错误来源是换行、串行、小数点、上下标误读 —— 全都可以通过重看原图修正。

**后果:**

- 每条规则带 `on_failure` 属性:`reread` / `flag` / `ignore`
- **先验有边界**:跨仪器差异(iSTAT Hb 126 vs 血球仪 130)、跨标本类型、参考区间冲突 —— 这些差异**是真实的**,重读一百遍还是那样,必须标 `flag` 而非 `reread`,否则闭环永不收敛
- 新增 **Tier 0 结构完整性校验**(编号连续、行数匹配、必填列非空、跨页衔接)—— 这是唯一能捕获"漏读整行"的手段,数值层校验对此完全无感
- 重读是**针对性**的:由失败规则定位涉及字段 → 取 `source_bbox` → 裁剪该区域 + 表头。更便宜(token 少)也更准(每字符像素数更高)
- `source_bbox` 从"方便人工核对"升级为**闭环的必需输入**
- `extraction` 增加 `round` / `triggered_by` / `parent_extraction_id`;同一 version 共享,每轮留档
- 终止:最多 3 轮,每轮失败数必须严格下降,否则转人工

**与 ADR-016 的关系:** 这让确定性校验的地位**变强**。它不再只是"标红给人看",而是**闭环的控制器** —— 由它决定要不要重读、重读哪里。而这个角色**要求它独立于提取层**:若校验也由同一模型做,错误相关,它永远不会说"你读错了",闭环就永远不触发。

```
AI 读 → 确定性判定对错 → AI 带着判定结果重读 → 确定性再判定
```

**AI 负责读,算术负责判对错。两者必须来自不同来源,闭环才有意义。**

**何时重新考虑:** 若实测显示重读轮次收益极低(如 >95% 的失败在第 2 轮仍失败),则退回单轮 + 人工。

## ADR-040 · 判断归 AI,执行归确定性代码,判断本身持久化

> ⚠️ **部分修订于 ADR-045**:决策所引用的词表注册表须以快照形式随 `_meta/registries/` 落桶 —— 否则 decisions 离开代码仓库不可解读。

**决策:** 归一化层重构为三层:

- **判断层(AI + 决策缓存):** 决定"这是什么" —— 概念映射、单位识别(原文 → UCUM)、行合并/拆分(语义等价性)、异常标记语义、机构归一、就诊归组建议、药名剥离、PII 识别、趋势可比性评估
- **执行层(确定性,`packages/medical`):** 决定"怎么算" —— 换算算术、Tier 0/1 校验算术、派生公式、RCV;以及存储 key / sha256、`person_access` 过滤、`report_no` 幂等
- **决策层(`normalization_decision`):** AI 判断的输出被持久化、版本化、可人工确认;**同输入指纹 → 同决策,确定性重放**

**背景:** 4 组真实单据产生了约 20 条"固定规则",且出现了方向相反的一对 —— 用例 001:同名行**不可**合并(氧分压/氧分压(校正));用例 004:双语行**必须**合并(阴性/Negative)。区分标准只能用一段散文描述:「看值与参考区间是否语义等价」。**散文即 prompt —— 它描述的是语义判断,不是可编译的条件分支。** 固定规则表在中国医疗单据的异质性(同院同日列结构不同、图例与用法不一致、参考区间 7 天内漂移)面前不收敛,只会累积例外。方向由项目所有者明确提出,审核确认。

**后果:**

- **字典翻转:** `concepts.json` 从输入(人工维护的别名表)变为输出(已确认决策的导出快照,作冷启动种子)。别名空间无上界,人工维护必然永远缺条目;AI 兜底 + 确认晋升让它自然生长
- **可逆性护栏:** 映射类决策可撤销重放 → 高置信自动生效;**合并类决策有损 → 必须人工确认才生效**。一对方向相反的断言钉住判断边界:血气 HGB 与血常规 HGB 同概念不同设备,禁止合并(用例 001);COVID 双语行必须合并(用例 004)
- **低置信不映射**(不变式保留):`concept_code` 置 null,原值照常入库;决策表留 `proposed`,确认后重放补全
- **版本护栏:** 决策绑定 `model_id` + `prompt_version`;模型升级触发批量重评估生成新 `proposed`,**不静默替换已确认决策**
- **分层修正:** 已确认的决策属于**人工层**(与 `review_status` 修正同级),不可从原件重建 → 追加导出到 S3 `_index/decisions/` journal,维持「数据库可从 S3 完全重建」不变式(ADR-008)
- **对既有 ADR:** 016 / 039 不变 —— 执行层的确定性正是闭环成立的前提;037 的 ±12h 时间窗降级为 AI 归组建议的先验与无 AI 时的兜底;035 的「由上下文判断」显式落在判断层
- **成本:** 归一化为纯文本调用(~0.01 元/张);稳态缓存命中率预计 >90%,仅新指标/新医院触发 AI

**何时重新考虑:** 若确认队列持续积压成为瓶颈,重新评估哪些决策类型可自动晋升;若某类判断的 AI 准确率实测低于表驱动,该类退回固定表。

## ADR-041 · P0 上传链路修复:key 去语义化、治理模式、本地归人确认

> ⚠️ **部分修订于 ADR-045**:锁不用桶级默认保留期,改按权威矩阵逐对象设置;views 迁至 `derived/_views/`;manifests 只收 L1 事实事件(add/归人纠正),分类改判不进 manifests;JSONL 追加一律条件写。

**决策:**

1. **S3 key 收缩为只含上传时已知的成分**:`people/{person_slug}/{YYYY}/{capture_date}__{doc_short_id}/`。facility / doctype / 采样日期的可读性移到 sidecar 与 `_index/views/`(可重写的视图文件,不受锁约束)。
2. **对象锁从合规模式改为治理模式**;versioning 保留。仍防代码 bug 与误删(需显式特权绕过),换来纠错能力;"存一辈子"由 versioning + 双备份 + 月度校验共同承担。
3. **归人确认在拍照现场本地完成**(手选家庭成员列表,离线可用,单人家庭一键);AI 归人建议降级为上传后的**对账信号**:S1 读出的姓名与已确认归人不一致 → `person_mismatch` 告警进核查队列。
4. **manifests 定义修正行语义**:同 `doc_short_id` 后写覆盖先写;归人纠正写入修正行,`rebuild-index` 按"最后写入者胜"重放。
5. 批量导入路径允许暂缓归人(`status = needs_person_confirm`)+ 批量确认接口。

**背景:** 独立审核 C1/C2/C4 三条 critical:key 需要上传**之后** AI 才知道的语义 → 与预签名直传时序矛盾;合规锁 10 年禁删禁移 → key 写错永不可纠、生命周期规则不可执行、`PATCH doc_type` 改的是烧死在 key 里的值;归人流程在 01/05/07 三处互斥、`needs_person_confirm` 状态不可达;归错人的纠正无法传导到 S3,重建时错误复活。**共同根因:key 承载了事后才知道的语义。**

**后果:**

- 部分修订 ADR-008/009:「目录名一眼看出医院与类型」降级为「`_index/views/` 与 sidecar 一读便知」
- 归人从"无法被校验发现的静默污染"(ADR-002)变为**可被 AI 对账发现** —— ADR-002 的强制确认原则不变,缺失的发现机制补上了
- 离线场景闭环:本地选人不依赖网络与 AI

**何时重新考虑:** 若 S3 服务商推出原子 rename 且与对象锁兼容(目前不存在)。

## ADR-042 · 序列身份开放化

**决策:** observation 的序列身份 = `concept_code` + `series_key`;`series_key` 是全部序列维度(qualifier / body_site / specimen / device / method / measurement_setting / extra_dims)映射的**确定性哈希**。新维度进 `extra_dims` jsonb + 维度注册表,**不再迁移唯一性键**。

**背景:** 审核 A F1:同一家医院 7 份单据已迫使约 15 次 schema 变更,唯一性键改了两次(ADR-023 加 qualifier、ADR-029 加 body_site);specimen 是排队中的第三次 —— 且已被自家 fixture 击穿(ADR-034 宣称"标本类型是分组维度",schema 枚举里却装不下末梢血/静脉血,fixture 001/004 的值互相矛盾)。这个斜率不会自己降下来。

**后果:**

- 已证实的维度保留为列(查询友好);未来维度零迁移
- `specimen` 改开放受控词表,立即补 `capillary_blood` / `venous_blood` / `nasal_swab`;文档级 `specimen` 字段补上(报告表头印着标本类型)
- `measurement_setting` 补列 —— ADR-019(血压独立数据流)此前在数据模型里**没有承载**
- `document_id` / `extraction_id` 改 nullable + `source` 枚举 —— 解开手动血压/体重**写不进库**的死锁(审核 A F4)
- 跨 series_key 不连线、不算 RCV(ADR-024/034 的实现形态统一)

## ADR-043 · 结构自我扩展机制(修订 ADR-040 的主张范围)

**决策:** 四件机制 + 一次诚实收窄:

1. **残差通道**:每个提取 schema 强制带 `unmodeled: [{label, value, region}]`,装不进 schema 的结构必须进残差,**禁止丢弃**。残差是"schema 该长了"的原始信号。
2. **`concept_mint` 决策类型**:AI 可提案新概念码 —— 须先对既有字典做语义近邻查重并显式声明"非同义",过命名 lint(确定性),人工确认后生效。铸造权补上,同义词分裂有闸。qualifier / body_site 同理(`body_site_map`)。
3. **`decision_type` 改注册表**(text + `packages/contracts` 注册表):每型注册指纹字段清单、确定性规范化规则(NFKC、去空白、上下文白名单)与可逆性标记。决策记录存规范化输入**原文**(自包含 —— 应用死后 journal 仍可重放,响应审核 B4/C3)。
4. **unknown 聚类监测**:`doc_type = unknown` 中积累同构单据达到阈值 → 自动生成"新增文档类型提案"进确认队列 —— 把"该造新类型了"从无人察觉变为显式信号。
5. **主张收窄**:"AI 自我扩展" = **词条级自动生长**(缓存 + 确认)+ **结构级半自动**(AI 从残差与聚类中提案 → 人确认 → 代码收编)。结构扩展永远经过人 —— 但人的角色从"写代码"降到"点确认"。

**背景:** 独立审核 A/B 一致结论:归档层自适应为真,结构层"自我扩展"名不副实 —— 铸造权真空(B1)、decision_type 封闭枚举自反(B2/A F5)、封闭 zod schema 在生成端物理掐死扩展且 `extraction.structured` 只是被裁剪结果的副本(A F2)、doc_type 四处硬编码且已失同步(A F6/B8)。

**后果:** 修订 ADR-040 的表述;doc_type 收敛 `packages/contracts` 单一来源;`report_narrative` 适用性由"报告含叙述段"判定,不由 doc_type 白名单判定;新增语义重复检测离线任务(input 相似而 output 不同的决策对 → 人工复核)。

## ADR-044 · 多 agent 角色架构(项目所有者提议)

> ⚠️ **部分修订于 ADR-045**:full_text 的地位从「与原件同级」改口为「与原件同**保留策略**,归属 L2 派生层」,落位 `derived/.../extractions/`。

**决策:** 系统显式采用**角色分离的多 agent 流水线**:每个 AI 角色有独立的上下文边界与目标函数;编排保持确定性;角色间**只通过持久化工件通信**(extraction / decision / flag / journal),不通过自由对话。

| 角色 | 职责 | 独立性要求 |
|---|---|---|
| 分类员 | S1:doc_type / 元数据 / 全文 | — |
| 提取员 | S2:按 doc_type 结构化 + 残差 | — |
| **盲审重读员** | 闭环重读 | **只收嫌疑格子坐标,看不到期望值与首轮读数** |
| 归一判断员 | 概念/单位/合并等决策提案 | 不参与提取 |
| 铸码提案员 | concept_mint(语义查重 + 提案) | — |
| PII 审计员 | 入索引前复查 pii_spans 覆盖 | **独立于提取员** —— 提取漏标由它兜底 |
| 对账员 | 归人 mismatch / 跨仪器 / 覆盖范围差异 | 只看结果工件,不看过程 |
| 策展员 | unknown 聚类、残差监测、规则 evidence_scope 追踪 | 后台低频 |
| **裁判** | Tier 0/1 校验 | **永远不是 AI** —— 确定性代码(ADR-016/039) |

**背景:** 三条论据:(1) 架构已在无意识收敛于此 —— ADR-039 读者/裁判、ADR-040 判断/执行、双次提取、对账规则,全是角色分离;本 ADR 只是命名并制度化。(2) 本项目的对抗审核就是实证:三个无历史包袱的独立 agent 找到 24 个长上下文当事人看不见的真实问题 —— **独立性本身产生信息**。(3) 审核 B5 恰是反例:重读员知道期望值 = 被污染的 agent,会把原件上真实的 34.1 "改写"成期望的 341.2 并以 passed 入库。修复的本质是**上下文隔离,而上下文隔离正是 agent 边界**。

**后果:**

- 修订 ADR-039 的重读规范:prompt **只报嫌疑格子,不给期望值**;重读结果恰好收敛到校验推算值且与首轮差异大 → 标 `converged_to_expected`,强制抽样人工复核
- 修订 ADR-031/015 的矛盾(审核 C-F8):full_text 分两层 —— sidecar 存带 PII span 标注的完整文本,入索引/embedding 前由确定性代码遮蔽;断言改为"**索引层**出现手机号即失败"
- 自我扩展闭环(ADR-043)运行在角色之间:提取员产残差 → 策展员聚类提案 → 人确认 → 注册表更新 → 提取员 prompt 再生成
- **不适用处:** 检索、趋势、存储、权限是纯确定性代码,不引入任何 agent

**三条铁律:** 编排确定性(通信走工件,保住可重放可审计);独立性 = 上下文隔离;裁判永远不是 AI。

**何时重新考虑:** 若实测显示角色隔离的成本(多次调用)超过其错误捕获收益,可合并低风险角色 —— 但盲审重读员与 PII 审计员的隔离不可合并。

## ADR-045 · 三层插件架构:L1 档案层自足且纯净,L2/L3 可整体替换(项目所有者提议)

**决策:** 系统显式分为三层 —— **L1 档案层(DMS)**:原件 + 拍摄事实 + 人工输入,10–20 年不淘汰,可整体打包迁移;**L2 数据处理层**:提取/转写/归一化/视图,持续完善,可整体重跑;**L3 分析层**:趋势/汇总/AI 分析,模型可随时切换(未来切到专业医学大模型)。L2/L3 是插件:**升级或替换时 L1 零字节变动;打包 L1 时不带走任何 L2/L3 工件。**

**背景:** 项目所有者提出该原则后的第二轮对抗性审核(两名独立审查员 + 当事人复核,22 条发现交叉收敛)判定:第一层在旧判据("档案活得比应用久")下及格,在新判据下三个方向同时不及格 ——

1. **混入**:`extractions/` 住在档案目录里;`document.json` 混装拍摄事实与 AI 观点(ADR-041 刚以同一理由把 facility/doctype 逐出 key,同一把刀没砍向 sidecar);音频转写焊死在录音 sidecar;full_text 被写成"与原件同级";全文档不存在"哪些对象不可变、锁覆盖哪里"的权威表。
2. **缺失**:问答的非语音答案、手动血压体重、监控组、person 的过敏史/慢性病/院内标识、归人裁决备注、audit —— 全部只活在"号称可重建缓存"的数据库里;其中三类连设计债都没登记。
3. **无打包定义**:没有导出格式;单人导出会因归人纠正后的物理错位拿错数据;桶不自足(schema/回放规则全在 git 仓库里)。

**后果(全部落 04 §1 权威矩阵,新增对象类型必须先登记):**

- sidecar 一分为二:`capture.json`(拍摄事实,WORM,上传瞬间即可写)+ `derived/.../meta.json`(AI 观点,可重写,provenance 必填)。判据:**上传瞬间就知道的进 capture,AI 提取后才知道的进 meta**
- L2 工件全部迁出 `people/`:extractions(改 `vNNN-rN` 每轮一对象)、transcripts、缩略图、views 全住 `derived/`,严禁上锁,打包可丢,备份不带
- **人工层 journal 立即建立**(D1 从 M8 提前):`people/{slug}/journal/{YYYY-MM}.jsonl`,写库事务内**双写**追加;收编问答全部答案类型、手动 observation、metric_group、person 编辑、归人裁决、encounter 编辑;`_person.json` 扩为全量快照(含过敏史/慢性病/identifiers);无文档会话原件落 `people/{slug}/context/`
- 归人纠正在文档目录追加 `correction-NNNN.json`;**key 中的 person 是拍摄时刻断言,权威归属 = manifests 回放**;月度校验两者一致
- 打包有了可执行定义:全量 = `people/ + _index/ + _meta/`(derived 可丢);单人导出 = 前缀 + manifests 按人过滤回放 + decisions 按共享词表/个人相关分类;bundle schema 进 contracts
- `_meta/` 自述层:桶根 README(布局/回放规则/journal 事件注册表)+ schema 快照 + 注册表快照 —— 解读档案的钥匙随档案走
- 锁**不用桶级默认保留期**,按矩阵逐对象设置;JSONL 追加一律条件写(etag)防并发丢行
- 修订:ADR-005(转写迁 derived)、ADR-008(sidecar 拆分)、ADR-040(decisions 词表快照随 `_meta` 落桶)、ADR-041(锁作用域、manifests 只收 L1 事实事件)、ADR-044(full_text 改口"与原件同保留策略,归属 L2")

**何时重新考虑:** 若逐对象锁在目标 S3 兼容实现上不可用,退回"桶默认保留 + derived 单独建桶"的双桶方案 —— 层边界升级为桶边界,原则不变。

## ADR-046 · 离线队列由前台驱动,Background Sync 只是 Chromium 加成

> 修订 [ADR-013](#adr-013--离线优先是-p0不是优化项) 的实现手段(其"离线优先是 P0"的决策不变)。

**决策:** 上传队列的推进由**前台事件驱动** —— 应用前台化 / `visibilitychange` 可见 / `online` 事件 / 可见时的定时扫描。Service Worker **不承担**队列推进,只做应用外壳预缓存。Background Sync 在支持的平台(仅 Chromium 系)上可作为额外触发,但**不得**成为任何承诺的依据。

**背景:** M1 spec 审核(#002)查证三条平台事实:

1. **iOS Safari 不支持 Background Sync**(Firefox 亦不支持),而 iOS 是本项目的主力场景 —— 医院里掏出来的是手机。
2. **Service Worker 读不到 `localStorage`**,而 token 存在那里;要让 SW 独立发请求,得把整个认证与队列引擎搬进 SW。
3. Background Sync 真正的价值场景是"页面已关闭时推进",而那时 `clients.matchAll()` 为空,没有任何页面可转发 —— 于是这条路径要么冗余(有页面 ⇒ 前台触发器已覆盖),要么无效(无页面 ⇒ 什么都做不了)。

**后果:**

- UI **必须如实**:队列非空时提示「保持应用打开直到上传完成」;**禁止**任何"关掉也会自动传"的暗示(CI 以文案 grep 断言,防实现期漂回)。
- ADR-013 决策句中的"Service Worker 后台重试"作废;docs/01 §离线优先流程图、docs/05、docs/09 同步回写。
- **存储持久性成为新的第一风险**:WebKit 对 script-writable 存储有"7 天无交互即清除"策略(已加入主屏幕的 Web App 豁免),而 Safari 不实现 `StorageManager.persist()`。因此队列必须在启动时请求持久化(能力存在时),未获授权时 UI 常驻降级提示并引导 iOS 用户"添加到主屏幕"。

**何时重新考虑:** iOS 支持 Background Sync,或本项目改做原生 App(那时后台上传由系统能力承担,ADR-013 的原始设想才成立)。

## ADR-047 · key 中的页号是拍摄序,`page_no` 是语义页序,二者允许分离

> 修订 [ADR-025](#adr-025--页序从页脚解析不依赖拍摄顺序) 的适用边界。

**决策:** S3 key 中的 `page-NN` 的 **NN 恒为拍摄序**(`capture_order`),写入即固定、永不改名;数据库的 `document_page.page_no` 是**语义页序**(ADR-025:从页脚「第 N 页,共 M 页」解析)。M1 无 AI,二者相等;M2 起可能分离,分离是**允许且预期**的。

**背景:** 两条约束相撞:①ADR-025 要求 `page_no` 来自页脚解析(实证:折叠的报告第 2 页先被拍到);②key 在上传瞬间就必须确定且此后永不改名(ADR-008/041/045,WORM 锁 10 年)。而页脚解析要等 AI(M2),上传等不了。

**后果:**

- `capture_order` 必须作为**拍摄瞬间即知的事实**进入 L1:`PageIn`、`capture.json.pages[]`、`document_page` 三处都有它。它是 M2 之后唯一能还原"当时怎么拍的"的凭证。
- 月度对账**不得**假定"key 中的 NN == `page_no`";要核对的是 key 中的 NN == `capture_order`。
- 展示与提取一律用 `page_no`;定位原件用 `storage_key`。二者之间的映射只存在于 `document_page` 行内。
- M1 期 `page_no := capture_order` 是**临时相等**,不是设计上的等价;实现者不得依赖这个巧合。

**何时重新考虑:** 若将来允许"上传后重排页序并改名对象",则本 ADR 与 WORM 原则冲突,须先推翻 ADR-045。

## ADR-048 · Cloudflare R2 作为 L1/L2 统一后端,WORM 由前缀锁 + 仅创建写 + 冷备三者合成

> 影响 [ADR-008](#adr-008)、[ADR-041](#adr-041)、[ADR-045](#adr-045--三层插件式架构),并要求 [ADR-049](#adr-049--journalmanifest-一事件一对象) 同批落地。

**决策:** L1 与 L2 都落 Cloudflare R2。R2 缺失的服务端 WORM 强制,由三条补偿措施合成:①L1 全部对象一律 `If-None-Match: *` **仅创建**写;②R2 **Bucket Locks** 对 L1 前缀设保留策略;③异地冷备到一份独立副本。三条缺一不可 —— 尤其②,因为 R2 无版本化,一次误覆盖不可恢复。

**背景:** 2026-08-18 对真实桶(`ai-medical-record`)跑 `pnpm probe-storage` / `probe-presign`,实测能力如下(证据是 R2 自己的响应码,非文档转述):

| 能力 | 结果 | 说明 |
|---|---|---|
| 条件写 `If-None-Match: *` / `If-Match`(含 412) | ✅ 完整 | **最关键的一条**:并发追加与仅创建语义都成立 |
| `PutObject` + `ChecksumSHA256`(服务端路径) | ✅ | |
| `CopyObject`(`_incoming` → 最终 key) | ✅ | 搬运链不变 |
| Multipart | ✅ | D14 可做 |
| 预签名 PUT | ⚠️ 可用,但**不得携带 `x-amz-checksum-sha256`** | 带该头必 403 `SignatureDoesNotMatch`(7 种变体逐一验证) |
| 预签名 PUT + `Content-MD5` | ✅ 且**真的强制**(错误摘要 → 400) | 直传完整性闸门的替代品 |
| 对象版本化 / `ListObjectVersions` | ❌ **501 NotImplemented** | 覆盖即永久丢失;A17 的 `(Key,VersionId,ETag)` 取证手段失效 |
| `PutObjectRetention`(逐对象治理模式) | ❌ **501 NotImplemented** | docs/04 §1 的 object-lock 列失去服务端逐对象强制 |
| 桶配置类(versioning/objectlock/cors/lifecycle) | ⚠️ 403 AccessDenied | 疑为 token 权限档次(需 **Admin Read & Write**),待复验 |

**为什么仍选 R2:** ①条件写是本项目并发模型的地基(journal/manifest 追加、幂等仅创建),它完整可用;②R2 有 **Bucket Locks**(前缀级保留,防删防覆盖,最多 1000 条规则),我们的 key 布局本就是前缀结构化的,天然可映射;③出网免费,而本应用的读取模式是持续取原图与派生物。

**必须诚实记录的代价:**

- R2 Bucket Locks **没有** compliance 模式与 legal hold,也无合规认证。它挡的是"误删/误覆盖",不是"持有凭证者蓄意销毁"。
- 无版本化 ⇒ **锁不是可选项**。没有锁的前缀,一次带 bug 的裸 PUT 就是永久数据丢失,连"回滚到上一版本"都没有。
- 逐对象保留期(不同对象不同到期)退化为按前缀统一保留期。

**后果:**

1. **上传链的校验和改道:**预签名 PUT 改签 `Content-MD5`(客户端在算 sha256 之外再算一次 MD5);服务端在登记步骤**下载并重算 sha256**,与客户端申报值比对,取代原先"读回存储侧 `ChecksumSHA256`"。这一改动使校验**不再依赖后端是否实现 flexible checksum**,反而更硬 —— 验的是真实字节。R2 出网免费,单页 ≤50 MiB,代价可接受。
2. **A17 取证手段替换:**`ListObjectVersions` 不可用,改用 `_index/l1-digest.jsonl`(key + sha256 + bytes 的清单,可完全从 `capture.json`/`page-NN.json` 重建)。这与 ADR-045 自洽:取证凭据本身也必须是 L1 可重建的。
3. **journal/manifest 必须改为一事件一对象**(ADR-049)—— 读-改-写在无版本化的后端上是不可接受的,且它与前缀锁直接冲突。
4. `provision-bucket` 需按后端分流:MinIO 走 Object Lock,R2 走 Bucket Locks;两者都必须跑**行为自检**而非配置自检(沿用 m1/CHANGES #2 的教训)。
5. 冷备是**必须项**而非增强项,且必须落到支持 Object Lock 的存储或离线介质。L1 可整体打包迁移(ADR-045 的设计红利)使这件事成本很低。

**Admin 档 token 复验结果(2026-08-18):**

| 项 | 结论 |
|---|---|
| CORS(`PutBucketCors`/`GetBucketCors`) | ✅ 经 S3 API 可配,已落地并通过 preflight 行为自检 |
| Lifecycle(`PutBucketLifecycleConfiguration`) | ✅ 已落地 `incoming-cleanup`(7 天 + 分片中止 1 天)与 `probe-cleanup` |
| `PutBucketVersioning` / `ListObjectVersions` | ❌ **501 NotImplemented**(admin 档下仍然)—— 确证 R2 无对象版本化,非权限问题 |
| `PutObjectRetention` | ❌ **501 NotImplemented** —— 确证无逐对象保留锁 |
| `PutObjectLockConfiguration`(`?object-lock`) | ❌ **501 NotImplemented**(`GET` 返 404 说明该 API 存在但无配置,`PUT` 未实现) |
| `?lock` 子资源 | ❌ 501 —— R2 Bucket Locks **不经 S3 API 暴露** |
| Cloudflare 控制面(`api.cloudflare.com`) | ⛔ 本开发环境的出网策略拒绝 CONNECT(403),无法从此处配置 |

**一个值得庆幸的细节:** R2 对带 `x-amz-object-lock-mode` 头的 `PutObject` 返回 **501 拒绝**,而不是静默忽略。这意味着现有 `s3.ts`(`putObject`/`appendJsonl` 都传 `ObjectLockMode: 'GOVERNANCE'`)在 R2 上会**每次 L1 写入都硬失败**,不会出现"以为上了锁其实没上"的静默降级 —— 后者才是真正危险的。代价是:**在 ADR-048/049 的实现落地之前,本应用无法对 R2 运行**。

**因此:** 补偿措施②(前缀级保留策略)**只能由项目所有者经 Cloudflare 控制台或 `wrangler r2 bucket lock` 配置**,或把 `api.cloudflare.com` 加进环境出网白名单后由脚本配置。在②与③落实之前,本桶不得承载生产 L1 —— `provision-bucket` 现在会把这一姿态原样打印,不再"自检通过"了事。

**同批落地的实现改动:** `provision-bucket` 改为**探测后端能力再分流**(而非假定 S3 语义),并如实播报 WORM 姿态;`s3-admin` 的签名区域按后端选择(R2 须 `auto`),MinIO 的 Content-MD5 兼容中间件对 R2 关闭;CORS 的 `AllowedHeaders` 取并集(同时含 `x-amz-checksum-sha256` 与 `content-md5`)—— 少放一个头要重新取 admin 凭证,多放几个不构成风险,不对称,故取并集。

## ADR-049 · journal/manifest 一事件一对象

> 由 [ADR-048](#adr-048) 触发;修订 [ADR-040](#adr-040) 与 docs/04 §5 的追加写方式。

**决策:** `people/{slug}/journal/{YYYY}-{MM}.jsonl` 与 `_index/manifests/{YYYY}-{MM}.jsonl` 由"单文件读-改-写追加"改为**一事件一对象**:`people/{slug}/journal/{YYYY}-{MM}/{at}__{event_id}.json`、`_index/manifests/{YYYY}-{MM}/{created_at}__{event_id}.json`,一律 `If-None-Match: *` 仅创建。

**背景:** 现行 `appendJsonl` 是读整份 → 拼接 → 带 `If-Match` 整份回写。这套做法在 S3 + 版本化 + 治理锁下是自洽的:每次追加产生新版本,旧版本被锁住留存,历史仍是 WORM。**把版本化拿掉,这个前提就塌了** —— 回写会不可恢复地覆盖历史,而若给该前缀加保留锁,回写本身会被拒。两条路都走不通。

**为什么这不只是"迁就 R2",而是本来就更对:**

- 追加变成**天然幂等**:`event_id` 就是 key,重复上报直接 412,不需要台账(D17 因此可提前清偿)。
- 消除读-改-写窗口,`pg_advisory_xact_lock` 不再需要承担"保证 S3 回写顺序 == DB 提交顺序"的职责(M0 验收 A10×B5 抓到的那个缺陷,其成因整个消失)。
- 每个事件对象**写入即不可变**,可以直接进前缀锁 —— L1 的 append-only 从"应用约定"升级为"存储强制"。

**代价与缓解:** 对象数量增加,读一个月的 journal 从 1 次 GET 变成 1 次 LIST + N 次 GET。缓解:journal 是低频读;需要连续视图时,由 L2 物化一份紧凑投影(可重建,不进权威矩阵的 L1 行)。

**后果:**

- `buildKey.journal` / `buildKey.manifest` 签名变更,`parseKey` 与权威矩阵同步更新;`_meta/README.md` 的自述需说明新布局(否则第三方拿到桶读不懂)。
- `rebuild-index` 的 manifest 回放从"逐行"改为"逐对象",`event_id` 幂等逻辑不变。
- 迁移:M0/M1 期已产生的 `.jsonl` 保留原样并在 `_meta/README.md` 标注为历史布局;回放需同时认两种布局(旧只读)。
