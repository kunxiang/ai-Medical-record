# 11 · 微信小程序合规调研(政策与审核)

> 调研日期:2026-08。对应 [09 · 路线图](./09-roadmap.md) 中「微信小程序 —— 需先核实医疗健康类目资质要求 🔍」这一未决项。
>
> **本文只谈政策与审核,不谈技术移植。** 技术侧的已知代价(离线队列重写、无 Service Worker)见 [01 §4](./01-architecture.md#4-多平台演进)。
>
> 🔍 = 需向平台客服 / 专业律师核实的判断,不要当结论用。

## 0. 结论先行

**以当前设计形态,本项目上不了微信小程序。** 卡点不是一条,是三条相互独立、必须同时解决的硬阻断:

| # | 硬阻断 | 现状 | 能否绕过 |
|---|---|---|---|
| 1 | **个人主体不开放医疗类目与深度合成类目** | 个人项目 | ✗ 只能注册企业主体 |
| 2 | **AI 功能需算法备案;Claude API 不可能有中国备案** | ADR 全线依赖 Claude 视觉能力 | ✗ 只能换境内已备案模型 |
| 3 | **医疗类目资质四选一,全部要求医疗机构/器械身份** | 个人档案工具,不是医疗机构 | △ 只能通过**功能降级**避开医疗类目 |

第 1、2 条是"补材料就能过"的成本问题;第 3 条是**产品定位问题** —— 也是本文最值得读的部分:
**"档案工具"能上,"化验单解读工具"上不了,而本项目的 P2/P3 恰好踩在这条线上。**

同一件事在两套体系下判定不同,不要混淆:

- **NMPA(是不是医疗器械):** 本项目处理对象是**报告单照片**,属"非医疗器械数据",大概率**不按医疗器械管理**(见 §2.8)。
- **微信平台(能不能上架):** 与是否医疗器械**无关**,只看审核员判定你落哪个服务类目。这才是真正的门槛。

## 1. 三道闸门

顺序过,任一不过就到不了下一道。很多人只准备了第三道。

```
① 主体资格          ② 工信部小程序备案(ICP)      ③ 类目资质 + 代码审核
   个人 / 企业            涉医服务内容需前置审批         类目资质 + 名称 + 隐私指引
   ▲ 本项目卡在这         ▲ 涉医则卡在这               ▲ 本项目卡在这
```

小程序 ICP 备案自 2023-09-01 起为**上架前置条件**(工信部信管〔2023〕105 号),存量小程序 2024-04-01 起清退。备案时要填「服务内容」,涉及医疗健康的需提供**卫健等主管部门的前置审批文件**才能通过 —— 这意味着即使微信平台放行,通信管理局这一关也拦得住。

## 2. 逐项难点

### 2.1 主体资格 —— 个人主体是死路

微信对个人主体小程序的开放类目遵循"非经营、低风险、工具化"原则:日历、计算器、单位换算之类。**医疗健康类目对个人主体完全不开放**;更要命的是,**深度合成类目同样不对个人主体开放**。

社区可查的 2026-01 驳回原文:

> 小程序服务内容涉及深度合成技术(如 AI 问答、AI 换脸视频、AI 绘画等),属个人主体尚未开放服务类目 —— 建议申请企业主体类型小程序。

**结论:** 只要小程序里有任何 AI 生成/合成能力(本项目的提取、转写、语义检索问答都可能被这样判定),**必须企业主体**。这一条先于其他一切:没有营业执照,后面的类目、备案、算法备案全都无从谈起。

### 2.2 服务类目资质 —— 本项目一张证都拿不到

| 候选类目 | 所需资质 | 本项目 |
|---|---|---|
| 医疗-其他医学健康服务 | 四选一:《医疗机构执业许可证》/《医疗器械生产许可证》/ 合作医疗机构协议 / 供应商医疗器械备案凭证及供货合同 | ✗ 全部拿不到 |
| 医疗-就医服务 | 卫健委批文 + 合作医院列表与协议 | ✗ |
| 医疗-互联网医院 | 互联网医院牌照 | ✗ |
| 资讯-信息资讯 | 《非经营性互联网信息服务备案核准》 | ✓ 可拿,但**不能承载**报告识别与指标功能 |
| 工具 / 效率类 | 一般无特殊资质 | ✓ 可拿,但有**超范围经营**风险 |

**这是本项目最核心的困难。** 微信医疗类目的资质设计前提是"你是一家医疗机构或其合作方",而本项目的定位恰恰是**个人自己管理自己的纸质单据** —— 这个用户身份在类目体系里没有位置。

超范围经营的后果不是"审核时被拒"这么简单:

> 小程序存在相关行业服务内容但未申请通过相关服务类目的,平台将提醒开发者限期调整;开发者未申请相关类目或未移除相关服务的,平台将视违规程度**限制部分功能或封禁小程序**。

而且**可被用户举报** —— 开放社区里"高危服务类目不符"的投诉贴是常态。也就是说,以「工具」类目上线一个会识别化验单、画指标趋势的小程序,不是"能不能过审"的赌博,而是**一颗上线后随时可能引爆的雷**,且档案类应用一旦被封,用户的数据资产直接受损,这与项目"档案要活得比应用久"的第一性原则正面冲突。

🔍 **待核实:** 「纯拍照归档 + 全文检索、不做任何指标提取与趋势」是否可稳定归入工具类目而不被要求补医疗类目。建议提交前用类目详情页的人工客服问一次,并留存答复截图。

### 2.3 AI 功能 —— 深度合成类目 + 算法备案

法规链条:《互联网信息服务深度合成管理规定》(2023-01-10 施行)+《生成式人工智能服务管理暂行办法》(2023-08-15 施行)。

微信「深度合成-AI问答」类目要求提交:

- **小程序主体自身**的《互联网信息服务算法备案》系统截图(算法类型为"生成合成类"),**或**
- **技术提供方**的算法备案截图 **+** 小程序主体与技术主体的**合作协议**

对本项目的直接后果:

- **Claude API 走不通。** Anthropic 不是中国境内算法备案主体,拿不到备案号,也签不了这个意义上的合作协议。面向境内公众提供服务时使用未备案境外模型,本身即属违规。
- **必须切换到境内已备案大模型**(通义千问 / 文心 / 豆包 / 混元 / GLM 等),并从模型厂商处取得备案号与合作协议 —— 这些厂商通常提供现成的"上架合规材料包"。
- **责任不随模型转移。** 即使用了第三方已备案模型,小程序主体仍是《暂行办法》意义上的**服务提供者**,内容审核、语料安全、拒答能力、标识规范等义务一样都少不了(参见《生成式人工智能服务安全基本要求》所列 31 类安全风险场景)。

🔍 **判定边界(本项目特有的灰区):** 本项目的 AI 是**提取 / OCR / 转写 / 检索**,不是"AI 问答"。纯 OCR 长期被视为识别类而非生成类。但本项目有三处会把它推向生成合成侧:

1. 语音转写(ASR)+ 转写文本入库([06](./06-ai-pipeline.md));
2. 语义检索的自然语言查询([01 §5](./01-architecture.md#5-检索));
3. 情境问答的自由文本输入与整理([05](./05-capture-and-context.md))。

**保守假设:要备案。** 按"不备案 → 上架被拒 → 重做"的代价算,提前按需要备案设计更划算。

> 对本项目架构的启示:[ADR-045](./adr.md#adr-045) 把 L3 分析层设计为可插拔,**恰好就是这次换模型的逃生舱**。境内模型替换只动 L2/L3,L1 档案层零字节变动 —— 这个决策的价值在合规场景下比在技术场景下更大。

### 2.4 AI 生成合成内容标识(2025-09-01 起强制)

《人工智能生成合成内容标识办法》(网信办等四部门)要求:

- 生成合成的文本、音频、图片、视频**添加显式标识**;
- 文件元数据中**添加隐式标识**(内容属性、服务提供者名称/编码、内容编号);
- **提供下载、复制、导出功能时,必须确保文件含符合要求的显式标识**;
- **应用分发平台在上架审核时核验标识相关材料。**

对本项目的具体落点:

| 产物 | 是否需标识 | 说明 |
|---|---|---|
| AI 提取的 `full_text`、结构化读数 | 🔍 很可能需要 | 展示处应标注"AI 识别,请核对原件" |
| 语音转写文本 | 是 | 典型的生成合成内容 |
| M7 导出的一页纸 PDF | 是(若含 AI 产物) | **导出=下载,显式标识是硬要求**;隐式标识要进 PDF 元数据 |
| 分享链接页面 | 是 | 同上 |
| 原件影像 | 否 | 拍摄事实,非生成物 |

**设计上的好消息:** 项目原则三「不生成医学结论」与 M7「导出明确不含任何 AI 解读」([09 §M7](./09-roadmap.md#m7--就诊导出))意外地**大幅减轻了标识义务** —— 导出物越接近"原件 + 人工确认过的数值",需要打 AI 标识的成分越少。这条产品原则在合规上是资产,不是约束。

### 2.5 数据出境 —— 调用 Claude API 就是出境

健康医疗信息属《个人信息保护法》第 28 条明列的**敏感个人信息**。本项目上传的原件影像还额外含姓名、证件号、就诊机构 —— 一张化验单照片就是一份完整的敏感个人信息包。

《促进和规范数据跨境流动规定》(2024-03-22)的分级:

| 出境规模(自然年累计) | 合规路径 |
|---|---|
| 非敏感个人信息 < 10 万人 | 豁免 |
| 非敏感 10 万–100 万人 **或 敏感个人信息 < 1 万人** | **订立个人信息出境标准合同并向省级网信部门备案**,或通过个人信息保护认证 |
| 非敏感 ≥ 100 万人 **或 敏感 ≥ 1 万人** | 申报数据出境安全评估 |

**敏感个人信息没有数量豁免档。** 哪怕只有一家人的档案,只要出境就落在"标准合同 + 备案"这一档,还要叠加单独同意与个人信息保护影响评估。

再叠加《国家健康医疗大数据标准、安全和服务管理办法(试行)》(国卫规划发〔2018〕23 号):健康医疗大数据应当**存储在境内**安全可信的服务器上,确需向境外提供的须安全评估审核。🔍 该办法的责任主体是医疗卫生机构等"责任单位",个人应用是否被涵盖存在解释空间,但在小程序审核语境下,审核员**不会替你做有利解释**。

**结论:** 与 §2.3 指向同一个动作 —— **模型换境内、对象存储换境内**(阿里云 OSS / 腾讯云 COS)。[04 · 存储布局](./04-storage-layout.md) 依赖的 Object Lock(治理模式)、versioning、生命周期规则在境内云上均有对应能力,但**具体行为差异需实测**🔍,尤其是"治理模式 + 逐对象保留期"的组合。

### 2.6 敏感个人信息与"替家人建档"

这是本项目**与普通健康类小程序最不一样、也最容易被忽略**的合规点。[00 §5](./00-vision-and-scope.md#5-用户与场景) 明确:家庭成员不使用应用,由所有者代为建档。

| 义务 | 依据 | 对本项目 |
|---|---|---|
| 单独同意 | PIPL 29 | 不能混在总的隐私协议里一次勾选,健康数据须**单独**弹窗 |
| 事前个人信息保护影响评估(PIA)并记录 | PIPL 55/56 | 处理敏感个人信息强制,须留档 |
| 告知处理必要性与对个人的影响 | PIPL 30 | 隐私指引里要写清"为什么要传原件、AI 会看到什么" |
| **不满 14 周岁 → 监护人同意 + 专门处理规则** | PIPL 31 /《儿童个人信息网络保护规定》 | fixture 001 就是儿科急诊 —— 这是**主线场景,不是边角** |
| 代他人处理 | PIPL 13/14 | 给配偶、父母建档需**本人**同意;成年家属并非"监护"关系 |

现有设计能直接复用的部分:`person_access` 授权表([01 §3](./01-architecture.md#3-多用户演进))已经是天然的授权载体,PII 最小化提取([ADR-031](./adr.md#adr-031))与独立的 PII 审计员角色([ADR-044](./adr.md#adr-044))也是实打实的加分项。

但要说清楚:**PII 最小化管的是"内部扩散",不能替代"告知—同意"。** 上小程序需要新增的是同意链路本身:

- `person_access` 上补一列同意证据(谁、何时、以何种方式同意);
- 未成年人档案的监护关系声明与成年后的转移路径(与 [04 §单人导出](./04-storage-layout.md#单人导出孩子成年带走自己的档案) 的"孩子成年带走档案"正好衔接);
- 小程序《用户隐私保护指引》逐项声明:相机、相册、麦克风、以及**从影像中识别出的姓名/证件号**。自 2023-09-15 起,必须先同步"用户已阅读并同意"才可调用隐私接口(`wx.requirePrivacyAuthorize`),否则接口直接失败。

### 2.7 分享链接与导出

M7 规划的"有效期可控的分享链接"([09 §M7](./09-roadmap.md#m7--就诊导出))在小程序语境下等价于**向不特定第三方提供敏感个人信息**。最低要求:强制过期、可撤销、访问留痕、页面带 AI 标识与水印,且**默认不含原件影像**(原件含证件号)。

### 2.8 医疗器械边界 —— 这条反而是好消息

《人工智能医用软件产品分类界定指导原则》(NMPA 2021 年第 47 号)的判定逻辑:

- 处理对象为**医疗器械数据**,且核心功能是对其处理/测量/模型计算/分析并用于医疗用途 → 按医疗器械管理;
- 处理对象为**非医疗器械数据**(明确举例:患者主诉等信息、**检验检查报告结论**),或核心功能不是对器械数据处理,或不用于医疗用途 → **不作为医疗器械管理**;
- 若按器械管理:非辅助决策(数据处理、测量,提供临床参考信息)→ **二类**;辅助决策(病灶识别、性质判定、用药指导、治疗方案)→ **三类**。

**本项目的处理对象是报告单的照片,即"检验检查报告结论",落在"不作为医疗器械管理"的举例里。** [00 §3 非目标](./00-vision-and-scope.md#3-非目标) 里"不做诊断/不做治疗建议/不判定正常异常"的自我约束,恰好把项目稳稳地钉在这一侧。

**但红线离得很近。** P3 的 RCV 提示「本次变化超出该指标的常规生物学波动范围」是全项目**最接近"提供临床参考信息"**的功能 —— 一旦被认定为医疗用途的测量与分析,对应的就是二类器械。[00 §4](./00-vision-and-scope.md#4-允许的中性提示) 的"关于数据本身的陈述,而非关于健康状况的判断"这个区分是有效的辩护,但它是**产品文案层面**的辩护,需要在 UI、导出物、小程序简介、免责声明里**一致地**呈现,才能在审核与监管场景下立得住。

⚠️ **不要混淆两件事:不按医疗器械管理 ≠ 不需要平台类目资质。** §2.2 的门槛与本节无关,不会因为"我们不是医疗器械"而降低。

### 2.9 小程序名称

名称命中医疗关键词时,需提供《医疗执业许可证》;若业务与医疗无关,则需用《商标注册证》或商标授权书证明。

**「AI 病历」这个名字必然命中。** 两条路:改名(避开"病历""医""诊""疗"等词,用无医疗指向的品牌词),或先注册商标再申请。改名更省事,但要注意 [00](./00-vision-and-scope.md) 里"给医生的佐证材料"这一定位如果原样写进小程序简介,同样会触发涉医判定 —— **名称、简介、功能描述三处口径必须一致且一致地"非医疗"。**

### 2.10 平台运营规范与当前监管气候

- **诊疗行为红线:** 平台允许"健康咨询"(如感冒吃什么),禁止实际的诊断与用药建议(如"你是病毒性流感,吃 XX 药")。本项目原则上不越线,但 AI 提取的自由文本一旦被用户追问、模型自由发挥,就可能越线 —— 这正是需要拒答策略与内容安全兜底的地方。
- **UGC 内容安全:** 小程序涉及用户输入内容的,需接入内容安全检测(`security.msgSecCheck` / `imgSecCheck`)。本项目有文本问答与语音转写,属于必须接入的范围🔍。
- **监管气候(重要):** 中央网信办 2026-04 起开展「清朗·整治AI应用乱象」专项行动,为期四个月、聚焦 14 类问题;第一阶段七类重点中就包括**未按规定履行大模型备案登记义务**、**生成合成内容标识落实不到位**、**平台安全与审核过滤能力不足**。官方通报的第一阶段处置量:违规网站/应用/智能体等 AI 产品 1.4 万余款。医疗被明确列为需**针对性设置行业领域安全审核与控制措施**的重点领域("AI 开处方"被点名)。

**这意味着 2026 年提交的 AI + 医疗健康小程序,面对的是近年来最严的审核尺度,不是历史经验能类推的。**

## 3. 三条路径

| | A · 不做小程序 | B · 降级为纯档案工具上小程序 | C · 完整功能合规上线 |
|---|---|---|---|
| 主体 | 无要求 | 企业(营业执照 + 认证) | 企业 |
| 类目 | — | 工具类🔍 | 医疗-其他医学健康服务 |
| 关键资质 | — | 无 | **四选一,均拿不到** |
| 模型 | Claude API 可留 | 境内已备案模型 | 境内已备案模型 + 自主/合作算法备案 |
| 存储 | 不限 | 境内 | 境内 |
| 保留功能 | 全部 | 拍照归档、检索、原件查看、情境问答 | 全部 |
| 砍掉功能 | 无 | **结构化提取、指标趋势、RCV、参考区间对照** | 无 |
| 周期估计 | 0 | 2–4 个月(注册公司 + 备案 + 类目 + 审核) | 不可达(除非成为医疗机构或其合作方) |
| 实质结论 | 保持现状 | **可行,但砍掉的正是 P2/P3 的全部价值** | **对本项目形态不可行** |

**推荐:A 为主,B 作为"入口"而非"全部"。**

理由:小程序真正不可替代的价值是**微信内的分享与打开路径**,而本项目最需要低摩擦的场景恰恰是"医院走廊里 10 秒拍照存档"—— 这个场景 PWA/App 已能覆盖,且不受平台封禁风险影响。若确实要小程序,把它定位成**采集端与查看端的轻壳**(拍照上传 + 检索 + 看原件),把提取、趋势、导出留在 Web 端,是唯一既合规又不牺牲核心能力的切法。

⚠️ **但要清醒:** 这个切法也不是零风险 —— 同一账号体系下,审核员可以主张小程序是"整体服务的入口",从而按整体服务判定类目🔍。这一点必须在提交前问清楚,而不是赌。

## 4. 若决定走 B,最小改造清单

按对现有设计的侵入程度排序:

| # | 改造 | 现有设计的支撑 | 侵入度 |
|---|---|---|---|
| 1 | L3 换境内已备案模型,取备案号 + 合作协议 | [ADR-045](./adr.md#adr-045) 分析层可插拔;L1 零字节变动 | 低 |
| 2 | S3 换境内对象存储 | [04](./04-storage-layout.md) 已抽象为 S3 兼容;Object Lock 行为需实测 | 低-中 |
| 3 | 同意链路:`person_access` 补同意证据列、未成年人监护声明 | 授权表已存在 | 中 |
| 4 | AI 标识层:展示端 + 导出物(PDF 显式 + 元数据隐式) | M7 已规定"不含 AI 解读",冲突小 | 中 |
| 5 | 内容安全接口接入(文本/图片) | 新增 | 中 |
| 6 | 分享链接改为强制过期 + 可撤销 + 留痕 + 默认不含原件 | M7 尚未实现,改设计比改代码便宜 | 低(现在改) |
| 7 | 隐私保护指引 + `wx.requirePrivacyAuthorize` 接入 | 新增 | 低 |
| 8 | 离线队列按小程序重写 | [01 §4](./01-architecture.md#4-多平台演进) 已预判不可移植 | 高 |
| 9 | 名称与简介去医疗化 | 需产品决策 | 低 |

**时机提示:** 第 3、6 两项现在改的成本近乎为零(尚未编码),M7 之后再改则要动数据与已发布的分享链接。即使最终不做小程序,这两项也是纯收益 —— 建议登记进 [design-debt](./design-debt.md)。
