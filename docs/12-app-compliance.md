# 12 · 原生 App 的合规调研(政策与审核)

> 调研日期:2026-08。承接 [11 · 微信小程序合规](./11-wechat-compliance.md) —— 那份文档的结论是"小程序上不了",本文回答下一个问题:**做成手机 App 是否更可行。**
>
> 🔍 = 需向平台 / 专业律师核实的判断,不要当结论用。

## 0. 结论先行

**App 比小程序根本性地好,但好在一个容易被忽略的地方:它有"不上架"这条路。**

一旦选择进国内应用商店,难点与小程序**基本同构**(备案 + 类目资质 + 算法备案 + AI 标识),某些方面还更重(软著、多商店各审各的、Apple 的 ICP 强校验)。

**真正的决定性变量不是"小程序 vs App",而是:是否面向不特定公众提供服务。**

| | 档 1 · 自用/家庭内 | 档 2 · 国内应用商店 | 档 3 · 仅境外区上架 |
|---|---|---|---|
| 分发方式 | APK 直装 / TestFlight / Ad Hoc | 华为、小米、OPPO、vivo、应用宝、App Store 中国区 | App Store 非中国区 |
| 主体 | 无要求 | 个人可注册,但涉医与 AI 类实际需企业🔍 | 个人可 |
| App 备案(工信部) | 🔍 见 §2.1 | **强制**,涉医需前置审批 | 不适用 |
| 类目/行业资质 | 无 | 医疗类要许可证,拿不到 | 无(但受 Apple 1.4.1 约束) |
| 算法备案 | 不需要 | **需要**(AI 功能) | 不需要 |
| AI 生成内容标识 | 不需要 | **需要**,分发平台上架核验 | 不需要 |
| **可否继续用 Claude API** | **✓ 可以** | ✗ 不可以 | ✓ 可以 |
| 数据可否存境外 | ✓🔍 | ✗ | ✓ |
| 被平台封禁下架的风险 | **无** | 高(涉医 + AI 双重敏感) | 中(Apple 医疗审核) |
| 能给多少人用 | 家人(iOS 有设备数限制) | 无限 | 无限 |
| 落地周期 | **即刻** | 3–5 个月 | 2–6 周 |

**推荐:档 1。** 而且不只是"最省事" —— 它是**唯一与项目第一性原则不冲突**的形态,见 §4。

## 1. 为什么"自用"这条路真实存在:PIPL 第 72 条

《个人信息保护法》第七十二条:

> **自然人因个人或者家庭事务处理个人信息的,不适用本法。**

这是俗称的"家庭豁免"。本项目的设定 —— 一个人给自己和家人建病历档案 —— 正落在这条的字面射程内。连带后果比想象中大:

| 义务 | 上架形态 | 自用形态 |
|---|---|---|
| 敏感个人信息单独同意、PIA 留档 | 强制 | 不适用 |
| 个人信息出境标准合同 + 备案 | 强制(见 [11 §2.5](./11-wechat-compliance.md#25-数据出境--调用-claude-api-就是出境)) | 🔍 不适用 —— 出境规则的义务主体是"数据处理者",家庭事务处理不在其列 |
| **能不能继续用 Claude API** | 不能 | **能** |
| 未成年人监护同意的形式要求 | 强制 | 不适用(你就是监护人) |

⚠️ **豁免的边界很脆,踩过去是瞬间的:**

- 给**家庭以外**的人用(哪怕免费、哪怕只有一个朋友)→ 豁免消失;
- **上架**任何商店 → 豁免消失;
- **收费** → 不仅豁免消失,还叠加经营性资质问题。

这对本项目有一个具体的警示:[01 §3 多用户演进](./01-architecture.md#3-多用户演进) 的 `person_access` 设计是为"未来多账号共享"预留的 —— 那个"未来"**就是豁免失效的那一刻**。结构上预留没问题,但要明确一条产品红线:**开放注册 = 从档 1 掉进档 2,合规成本从 0 跳到全额。** 建议把这条写进 [00 §3 非目标](./00-vision-and-scope.md#3-非目标)。

## 2. 档 2(国内上架)的难点:小程序那套全都在,外加四条

[11](./11-wechat-compliance.md) 里的三条硬阻断在这里**一条都没消失**:算法备案(Claude 走不通)、AI 内容标识、涉医资质。差别只有一处 —— 主体门槛松了一点:**应用商店接受个人开发者账号**,不像小程序医疗与深度合成类目对个人主体直接关门。但这个松动基本是名义上的:算法备案实务上要求企业主体🔍,医疗类资质更是只发给机构。

App 特有的额外负担:

### 2.1 App 备案(工信部信管〔2023〕105 号)

判断标准是**是否通过互联网提供服务**,不是"是否上架"。实务解读普遍偏保守:只要联网、服务器在境内,就建议备案;纯本地不联网的应用无需备案。

🔍 **本项目的自用形态处在解释空间里** —— 后端在自己的服务器上、只有自家人访问,是否属于"向上网用户提供信息服务",没有权威结论。可控的做法:

- 监管抓手实际在**应用商店与云服务商**(域名接入商会强制要求备案才能解析);
- 因此**要么把后端域名备案(个人非经营性备案即可,服务内容按工具类填,不要填医疗)**,要么走无公网域名的内网/局域网访问;
- ⚠️ **千万不要在备案的服务内容里填医疗健康** —— 那会触发卫健前置审批,直接卡死(见 [11 §1](./11-wechat-compliance.md#1-三道闸门))。

### 2.2 Apple 中国区的 ICP 强校验

中国大陆区 App Store 上架必须填写有效 ICP 备案号,存量 App 也在 2024-04 前被要求补齐,否则下架。后台会**自动校验 App 名称是否与工信部备案记录一致** —— 于是 [11 §2.9](./11-wechat-compliance.md#29-小程序名称) 的命名问题原样重现,而且更硬:名称、备案、商店三处必须完全一致。

**先例值得看清楚:** 2023 年苹果集中下架中国区 ChatGPT 相关应用,业内归因为**未做算法备案 + 数据跨境不合规** —— 这恰好就是本项目用 Claude API 的两条风险,已经有过一次实证。

### 2.3 软件著作权与多商店

华为等主流安卓商店要求提交**软件著作权登记证书**作为原创性证明(常规办理 30–60 天,加急另收费)。且各商店独立审核、口径不一,医疗健康类普遍要求企业主体 + 行业许可证。上架不是一次工作,是**五六次并行的工作,外加每次版本更新都要重过**。

### 2.4 上架后的持续合规

工信部对 App 违规收集使用个人信息的常态化通报是**上架后**的持续风险,与审核是两回事。相机、相册、麦克风这些本项目必用的权限,恰好是通报里的高频项。

## 3. 档 3(仅境外区)是另一套规则,不是"没有规则"

中国监管基本不适用,换来的是 Apple 的审核尺度:

- **1.4.1 医疗类:** 若对健康测量的准确性有任何主张,必须披露支撑数据与方法,无法验证即拒;必须提醒用户在做医疗决定前咨询医生。对本项目的直接含义:**不要宣称 OCR 读数的准确率**,免责声明必须显著且常驻。
- **5.1.1 / 5.1.3 健康数据:** 需要独立隐私政策;健康数据不得用于广告或营销,不得出售或共享给第三方。
- 若面向欧盟用户,叠加 GDPR(健康数据属特殊类别数据)。

🔍 **灰区:** 仅在境外区上架、但实际用户在境内使用,监管定性不明。不建议把它当作"绕开国内监管"的方案 —— 它是给海外用户的方案。

## 4. 这不只是合规问题,和项目第一性原则直接相关

[00 §6](./00-vision-and-scope.md#6-成功标准) 把"数据没丢"列为成功标准,README 的第二条原则是"档案要活得比这个应用久"。

在这个框架下,上架形态有一个**技术手段无法消除的结构性风险**:平台可以在任何时候以类目不符、资质缺失、AI 违规为由限制功能或下架应用,而档案类应用一旦被切断,用户的数据资产直接受损。小程序更甚 —— 它连"已安装的旧版本还能用"这个缓冲都没有。

**自用形态下,没有任何平台有资格封你。** 这与"档案要活得比应用久"是同一个方向的选择。App 相对小程序最本质的优势不是技术能力,是**治理上的自主权**。

顺带,档 1 还解掉了小程序方案里的一堆连带成本:

| 小程序方案要做的改造([11 §4](./11-wechat-compliance.md#4-若决定走-b最小改造清单)) | 档 1 是否还要做 |
|---|---|
| 换境内已备案模型 | **不用**,Claude API 可留 |
| 换境内对象存储 | 不用🔍 |
| AI 生成内容标识层 | 不用 |
| 内容安全接口接入 | 不用 |
| 隐私保护指引 + 隐私接口同步 | 不用 |
| 离线队列按平台重写 | 要(但 App 的能力**优于**小程序) |
| 同意证据链(D11) | 法律上不要求,**但仍建议做** —— 它同时是"孩子成年后带走档案"的前提 |
| 分享链接受控(D12) | 仍建议做 —— 分享链接一旦发给医生,就是向家庭外提供数据 |

D11/D12 保留的理由是产品性的,不是合规性的:见 [design-debt](./design-debt.md)。

## 5. 档 1 的实际形态与代价

| 平台 | 分发方式 | 代价 |
|---|---|---|
| **Android** | APK 直装 / 自建更新源 | **几乎零门槛 —— 最优形态** |
| iOS | TestFlight | 需过 Beta App Review(比正式审核宽松,但仍是审核);每个 build 90 天过期,要定期重传;中国区 TestFlight 是否需备案🔍 |
| iOS | Ad Hoc(99 美元开发者账号) | 每年 100 台设备上限,证书年度续期,重签后要重装 |
| iOS | 个人免费证书自签 | 7 天过期,不实用 |

**取舍很清楚:安卓侧自用是完全自由的,iOS 侧永远有一道苹果的手。** 如果家里主力是 iPhone,TestFlight 是最现实的路,代价是每 90 天重传一次 —— 对一个自用工具可以接受,但要提前知道。

> 与 [01 §4](./01-architecture.md#4-多平台演进) 的既有判断一致:PWA 仍是成本最低的起点,只有在**拍照与录音遇到硬限制**时才值得上原生。合规层面并不构成"必须做 App"的理由 —— 它只是移除了"做了 App 也上不了架"这个顾虑。
