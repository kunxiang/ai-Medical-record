# 10 · 开发流程

> 项目所有者的工作习惯:**设计文档 → spec → 独立 spec 审核 → 处理 blocker → 实现**。
> 本文档把这个流程适配到本项目的特点,作为每个里程碑的固定循环。

## 0. 本项目的特点决定的适配

| 项目特点 | 对流程的影响 |
|---|---|
| 设计已冻结(00–09 + 45 条 ADR,经两轮对抗性审核) | spec 阶段**不再讨论设计对错** —— spec 与设计文档冲突时,要么 spec 改,要么走 ADR 修订,没有第三条路 |
| AI 管线已有 fixtures 作为行为基准 | fixtures **就是提取管线的 spec**(期望输出 + 断言)。specs/ 只覆盖工程侧;两者验收地位等同 |
| 里程碑各自独立可验收(09) | **spec 按里程碑写**,不写全系统大 spec —— M0 的 spec 不为 M5 的问题负责 |
| 独立审核已被证明有效(两轮共 46 条真实发现) | spec 审核沿用同一机制:≥2 个独立对抗视角 + 当事人复核 + 合议分档 |
| 个人项目,单人决策 | blocker 裁决不开会 —— 合议报告给项目所有者,批准后执行 |

## 1. 每个里程碑的循环

```
① Spec 起草          specs/mN/ —— 精确到实现者不需要做任何决定
        ↓
② 独立 spec 审核     ≥2 个对抗视角,审的是:歧义 / 欠定 / 与设计文档的偏差 /
        ↓            不可测的验收项 / 里程碑边界泄漏 —— 不是审设计
③ Blocker 分档       A 档:欠定或矛盾,开工前必须修 spec
        ↓            B 档:实现期可解,写进 spec 的"实现注记"
        ↓            C 档:登记 design-debt,绑定后续里程碑
④ 实现               验收清单(99-acceptance)先行 —— 每条断言可执行
        ↓
⑤ 里程碑验收         99-acceptance 全绿 + fixtures 回归全绿 + 设计债到期项清偿
```

## 2. Spec 的写法(specs/README.md 是权威约定)

- **规范性语言**:必须 / 禁止 / 应当 / 可以(RFC 2119 语义)。"建议""最好"不出现在规范性条文里。
- **每条可测**:验收项写成命令或断言,跑得出通过/失败;跑不出的不叫验收项。
- **决定,不讨论**:设计文档回答"为什么",spec 只陈述"是什么"并给出精确值(字母表、BNF、DDL、错误码)。留白必须显式标注 `[欠定]` 等待审核裁决,不允许隐式含糊。
- **偏差显式化**:spec 与设计文档不一致处,必须标注 `[偏差:vs 03 §x]` 并给理由 —— 审核员据此逐条核对。

## 3. 设计变更的唯一通道

实现或 spec 阶段发现设计错误 → **走 ADR**(追加或修订,按 README 的 D8 checklist 同步),然后 spec 跟着改。禁止 spec 或代码悄悄偏离设计文档 —— 三份真相(设计/spec/代码)失同步是本项目审核实证过的系统性风险。

```

    ├── …              # 分主题的规范性条文
    └── 99-acceptance.md  # 验收清单,逐条可执行
```
