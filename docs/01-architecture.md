# 01 · 系统架构

## 1. 分层

```
┌──────────────────────────────────────────────────────────┐
│  客户端(薄)                                              │
│  PWA(P0) · App(未来) · 微信小程序(未来)                │
│  职责:采集、展示、离线队列。不含业务逻辑。                 │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS / REST (packages/contracts 定义)
┌───────────────────────▼──────────────────────────────────┐
│  API 服务(厚)                                            │
│  鉴权 · 归档 · 人工事实 · 关键词检索 · 趋势 · 导出队列     │
└──┬──────────────┬──────────────┬──────────────┬──────────┘
   │              │              │              │
┌──▼───────┐  ┌───▼────────┐  ┌──▼─────────┐  ┌─▼────────┐
│ S3 兼容   │  │ PostgreSQL │  │ 关键词索引  │  │ export worker│
│ 对象存储  │  │ 索引/队列   │  │ (可重建)   │  │ PDF/PNG    │
│ ★L1 真相 │  │ (可重建)   │  │ 语义可选增强│  │ 确定性    │
└──────────┘  └────────────┘  └────────────┘  └──────────┘
```

可选 `plugin-main` worker 独立连接模型/ASR 供应商，只产生待确认 L2 建议；不部署它时 Core 保持完整。

**★ 唯一的持久真相是 S3 中的原件与 sidecar JSON。** 数据库和检索索引都是可从 S3 完整重建的缓存。这一条决定了很多下游设计。

**★ 三层插件架构([ADR-045](./adr.md#adr-045)):** L1 档案层(原件 + 拍摄事实 + 人工输入 —— 10–20 年不淘汰,可整体打包迁移)/ L2 数据处理层(确定性索引/导出工件与可选 AI 建议 —— 可整体重建)/ L3 分析层(可选的后续分析，不属于 P0–P4 Core)。L2/L3 可替换:**升级或删除时 L1 零字节变动;打包 L1 不带走任何派生物。**"数据库可重建"的前提是人工输入随写随双写 journal,而不是等某个导出功能。对象归属的权威表见 [04 §1](./04-storage-layout.md#1-权威矩阵对象--层--可变性--锁--打包)。

`PROCESSING_MODE=off` 是 Core 默认值。API 进程不加载 provider adapter；`plugin-main` 独立消费 processing job，可不部署。`export-main` 是 Core 确定性 worker，与 AI 插件无关。发布门禁分轨见 [ADR-051](./adr.md#adr-051--p0p4-core-与-ai-插件资格分轨)。

## 1b. AI 层的形态:多角色代理系统([ADR-044](./adr.md#adr-044))

AI 管线不是"一个大模型一把梭",而是**多个窄职责角色 + 确定性编排**:

```
                    确定性编排器(代码,不是 AI)
                            │ 按状态机调度
   ┌────────┬────────┬──────┴─────┬──────────┬─────────┐
   ▼        ▼        ▼            ▼          ▼         ▼
 分类员   提取员   盲审重读员   归一判断员   PII审计员  对账员/策展员…
 (每个角色:独立上下文、窄 prompt、结构化输出、只读黑板)
   │        │        │            │          │         │
   └────────┴────────┴─────┬──────┴──────────┴─────────┘
                            ▼
              黑板 = 版本化工件(extraction / decision / sidecar)
                            │
                            ▼
              裁判 = Tier 0/1 确定性校验(纯代码,永远不是 AI)
```

三条铁律:

1. **裁判永远不是 AI** —— 对错由算术与结构校验判定,AI 只负责读和判断语义
2. **角色间不共享上下文** —— 通过黑板(持久化工件)通信,盲审重读员看不到提取员的读数
3. **编排是确定性代码** —— 谁在什么条件下被调用是状态机,不是模型自由发挥

角色清单、职责边界与新增角色的规则见 [ADR-044](./adr.md#adr-044);各角色的 prompt 与 schema 见 [06 · AI 管线](./06-ai-pipeline.md)。

## 2. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript**(前后端统一) | 类型契约跨端共享是多平台策略的核心;单语言降低维护成本 |
| 后端框架 | **Fastify** | 轻量、快、TS 友好。NestJS 亦可,但对个人项目偏重 |
| 数据库 | **PostgreSQL 16+** | 关系模型 + JSONB + `pgvector`,一个库解决结构化与向量 |
| ORM | **Drizzle** | 类型推导好,迁移可读,不隐藏 SQL |
| 对象存储 | **S3 兼容** | 见 [04 · 存储布局](./04-storage-layout.md) |
| 前端 | **React + Vite + PWA** | Service Worker 是离线队列的前提 |
| 检索 | 见下方 §5 | |
| AI | **可配置视觉模型 API**(DeepSeek/Anthropic)+ **独立 ASR**(语音) | 见 [06 · AI 管线](./06-ai-pipeline.md) |
| 部署 | Docker Compose(单机起步) | |

### 为什么 API-first

两个约束把架构推向同一个方向:

1. **AI 密钥绝不能进前端** → 所有 AI 调用只能在独立 plugin worker
2. **未来要支持 App 和小程序** → 业务逻辑必须与 UI 解耦

结论:**客户端只做采集与展示,所有逻辑在服务端**。换平台时只需重写一层壳。

## 3. 多用户演进

初期只有一个账号,但**结构上从第一天就是多用户的**。核心是不把 `person` 直接挂在 `account` 下,而是用一张授权表:

```
account ──┐
          ├──> person_access (account_id, person_id, role) ──> person
          │
   (Day 1: 一个 account,N 行 person_access)
   (Later: M 个 account,共享 person 只需加一行)
```

**为什么这样做:** 事后给已有表加租户键是代价最高的迁移之一;而多加一张两列的关联表,今天几乎零成本。它同时顺手解决了另一个真实需求 —— 夫妻共同管理孩子的档案,或子女共同管理父母的档案,只需要为同一个 `person` 加两行授权。

配套约束:

- **所有查询必须经过 `person_access` 过滤**,从第一天起就这样写。留一个能绕过它的查询路径,就是留一个未来的越权漏洞。
- 每张业务表都带 `person_id`,而非 `account_id` —— `person` 才是数据的归属主体。
- `audit_log` 记录 `account_id`(是谁操作的)和 `person_id`(动了谁的数据)。

## 4. 多平台演进

| 阶段 | 客户端 | 复用 |
|---|---|---|
| P0 | PWA(移动端浏览器) | — |
| 未来 | 原生 App | 复用 `contracts` + `medical`,重写 UI 与离线层 |
| 未来 | 微信小程序 | 复用 `contracts` + `medical`,重写 UI 与离线层 |

**可移植的部分:** API 契约、类型定义、医学计算(单位换算、参考区间、RCV、自洽校验)。这些被隔离在 `packages/` 下的**纯包**里 —— 零 I/O、零框架依赖,任何 JS 运行时都能跑。

**不可移植的部分:** 离线队列。小程序没有 Service Worker,存储 API 也不同,这部分必然要按平台重写。提前认清,不要为了"统一"而设计一个谁都不好用的抽象。

### 离线优先(P0 就必须做)

医院网络普遍很差 —— 地下室检验科、人多的门诊楼。**如果拍照后上传失败就丢了,系统在最关键的场景下失效,用户会失去信任并停止使用。**

```
拍照 ──> 立即写入 IndexedDB ──> 加入上传队列 ──> 前台驱动重试(ADR-046)
                 │                                      │
                 └──── UI 显示「3 张待上传」 ─────────────┘
                                                          │
                                            上传成功 ──> 清理本地
```

要点:

- 写入本地成功即视为"已存档",UI 立刻给正反馈
- 队列状态必须可见,让用户敢离开医院
- 大图走**预签名 URL 前端直传**,不过后端(省流量、省服务器)
- 大于 8 MiB 时使用 multipart 与 IndexedDB ETag 断点续传；对象完成后服务端回流校验整文件 SHA-256
- **队列推进由前台事件驱动**(ADR-046):iOS 无 Background Sync 且 SW 读不到 token,UI 必须如实告知

## 5. 检索

三条路径,覆盖不同的查找方式:

| 方式 | 实现 | 场景 |
|---|---|---|
| 维度筛选 | PostgreSQL 索引 | "2023 年 · 协和 · 化验单" |
| 全文关键词 | 见下 | "转氨酶"、"甲状腺" |
| 语义相似 | `pgvector` + embedding | "那次肝功能不太好的检查" |

**中文全文检索是个真实的坑。** PostgreSQL 原生分词不支持中文,需要 `zhparser` / `pg_bigm` / `pgroonga` 扩展,而托管 PG 服务不一定允许安装。

推荐路径:

1. **起步**:`pg_trgm` + `ILIKE` 兜底。数据量在万级以内完全够用,零额外依赖。
2. **数据量上来后**:引入 **Meilisearch**(中文支持好、部署简单、内存占用可控),或托管方案。
3. **语义检索**:`pgvector` 存 `extraction.full_text` 的 embedding,与关键词检索结果融合排序。

> ⚠️ **无论用哪个引擎,全文索引的源都是 `extraction.full_text`(AI 读出的完整文本)。**
> 结构化提取会失败,全文不会。这是档案系统的兜底 —— 哪怕表格解析全错,只要文本在索引里,就还能找到那份单据。

## 6. 关键数据流

### 归档(P0)

```
① 客户端拍照 + ★ 本地选人确认(1 次点击,离线可用)→ 写入 IndexedDB → 入队
② 请求预签名 URL → 直传原件到 S3(不可变区;key 由所选 person 决定)
③ 通知后端「已上传」→ 创建 document 记录(status=uploaded, person_confirmed=true)
④ Core 立即提供人工元数据、关键词索引和缩略图，文档不等待 AI
⑤ 可选 plugin worker 读取 L2 派生图生成元数据/OCR 建议并对账；不一致才提醒用户裁决(ADR-041)
⑥ capture.json(拍摄事实)与人工修正属 L1；AI 建议落 L2，删除后不影响归档、检索、趋势或导出
```

### 提取(P2)

```
document ──> extraction(v1, model=X, prompt=Y)
                 │
                 ├──> full_text ──────> 全文索引 + embedding
                 └──> structured ────> 归一化(判断:AI+决策缓存 / 执行:纯代码)
                                          │
                                          ├──> 算术自洽校验
                                          └──> observation 记录(带 review_status)
```

**重跑:** 未来模型变强时,对整个档案重跑提取生成 `extraction(v2)`,旧版本标记 `superseded`。已被人工确认(`confirmed`/`corrected`)的 observation 不被覆盖 —— 人工修正永远优先于机器提取。

## 7. 权衡记录

| 决策 | 取舍 |
|---|---|
| 单体后端而非微服务 | 个人项目,微服务是纯负担 |
| PostgreSQL 兼任向量库 | 少一个组件;数据量上来后可迁移 |
| TypeScript 而非 Python | 前后端共享类型的价值 > Python 的 AI 生态优势(本项目只调 HTTP API,不训练模型) |
| 服务端加密而非客户端加密 | 客户端加密会让服务端无法生成缩略图、无法 OCR、无法建全文索引 —— 所有智能都得搬到客户端。这是功能取舍,由项目所有者决定 |
| 不做实时协作 | 无此需求 |

```
S3_ENDPOINT / S3_BUCKET
S3_ACCESS_KEY / S3_SECRET_KEY
S3_REGION
BACKUP_TARGET              # 第二处备份(rclone remote)
JWT_SECRET

```

所有密钥仅存在于服务端。前端永远拿不到任何一个。
